# Git: ветки и merge

## Зачем это нужно

Ты уже умеешь сохранять состояние проекта коммитами. Но вот ситуация: проект работает, и тебе хочется попробовать рискованную идею — переделать оформление, переписать кусок кода. А вдруг не получится? Ломать работающую версию страшно, а копировать папку проекта «на всякий случай» — путь к хаосу из `project_final_2_new`. Для этого в Git есть ветка (branch) — параллельная линия истории. Ты сворачиваешь с основной дороги, экспериментируешь сколько хочешь, и основная версия при этом остаётся нетронутой: не вышло — просто вернулся обратно, как будто ничего и не было.

А если вышло — результат вливается в основную ветку одной командой: это называется слияние (merge). Так устроена работа любой команды разработчиков, и на чемпионате «Профессионалы» в том числе: каждый участник пилит свою задачу в своей ветке, а потом все изменения сливаются вместе. Иногда при слиянии Git встречает противоречие — конфликт (conflict). Звучит грозно, но на деле это обычная рабочая ситуация с понятным алгоритмом решения. В этой главе научимся создавать ветки, сливать их и спокойно разруливать конфликты.

## Как это работает

**Ветка — это не копия проекта.** Внутри Git ветка — просто лёгкая закладка, которая указывает на коммит. Поэтому создание ветки мгновенно и бесплатно: никакие файлы не копируются. Основная ветка обычно называется `main` — она появляется сама при первом коммите. Посмотреть все ветки: `git branch` (текущая помечена звёздочкой).

**Создать и переключиться.** `git switch -c fix-title` создаёт ветку `fix-title` и сразу делает её текущей. Дальше работаешь как обычно: правишь файлы, делаешь `git add` и `git commit` — все новые коммиты ложатся в эту ветку, а `main` стоит на месте. Вернуться назад: `git switch main` — и файлы в папке моментально принимают тот вид, какой был в `main`. В старых статьях вместо этого встретится `git checkout fix-title` и `git checkout -b fix-title` — это та же операция переключения (switch), просто старой командой; она до сих пор работает.

**Слить.** Когда эксперимент удался, встань на ветку-приёмник и позови к себе изменения:

```bash
git switch main
git merge fix-title
```

Если `main` за это время не менялся, Git делает перемотку (fast-forward): просто передвигает закладку `main` вперёд, на последний коммит ветки. Если же в `main` тоже успели появиться коммиты, Git объединяет обе линии и создаёт коммит слияния (merge commit) с двумя родителями. В обоих случаях от тебя больше ничего не требуется — если изменения не пересекаются.

**Конфликт — не катастрофа.** А вот если обе ветки изменили одни и те же строки одного файла, Git не станет угадывать, чья версия правильная. Он остановит слияние, напишет `CONFLICT` и вставит прямо в файл разметку из обеих версий:

```text
<<<<<<< HEAD
Название команды: Огонь
=======
Название команды: Молния
>>>>>>> new-name
```

Читается так: между `<<<<<<< HEAD` и `=======` — версия ветки, на которой ты стоишь; между `=======` и `>>>>>>> new-name` — версия ветки, которую вливаешь (`new-name` — её имя). Ничего не сломалось и ничего не потерялось: Git показал оба варианта и ждёт твоего решения. Алгоритм всегда один:

1. Открой файл в редакторе и найди маркеры `<<<<<<<`.
2. Оставь правильный текст: одну из версий, обе сразу или вообще новый вариант — решаешь ты.
3. Удали сами маркеры — все три строки с `<<<<<<<`, `=======` и `>>>>>>>`.
4. Скажи Git, что разобрался: `git add имя-файла`, затем `git commit`.

Всё. Слияние завершено, история цела. Конфликт — это не ошибка, а вопрос от Git: «тут два мнения, выбери».

## Потренируйся печатать

<CodeTyping snippet={'git switch main && git merge fix-title && git branch -d fix-title'} />

Кстати, `git branch -d fix-title` — это уборка: удаление закладки уже влитой ветки. Коммиты при этом никуда не деваются, они уже в `main`.

<details>
<summary>Углубиться</summary>

**HEAD.** В разметке конфликта ты видел слово `HEAD` — это указатель Git на «место, где ты сейчас стоишь»: текущую ветку и её последний коммит. Когда делаешь `git switch`, на самом деле перемещается именно HEAD. Поэтому «твоя» сторона конфликта подписана `HEAD`, а «чужая» — именем вливаемой ветки.

**Как Git сливает на самом деле.** При настоящем слиянии (не перемотке) Git сравнивает три снимка: последний коммит твоей ветки, последний коммит вливаемой и их общего предка — коммит, где ветки разошлись. Это называется трёхсторонним слиянием (three-way merge). Строки, которые менялись только с одной стороны, Git берёт автоматически — и только строки, изменённые с обеих сторон по-разному, объявляет конфликтом. Вот почему конфликты случаются реже, чем кажется новичкам.

**Разметку можно сделать информативнее.** Команда `git config merge.conflictStyle zdiff3` добавляет в разметку конфликта третий блок — как строки выглядели у общего предка. Часто именно это подсказывает, чья правка «новее по смыслу».

## Челлендж ⭐

Устрой конфликт своими руками и победи его. Сделай в терминале, шаг за шагом:

1. Создай папку `team`, зайди в неё и сделай `git init`. Создай файл `team.txt` со строкой `Название команды: пока думаем` и закоммить его.
2. Создай ветку `new-name` и переключись на неё одной командой. В файле замени строку на `Название команды: Молния`. Закоммить.
3. Вернись на `main`. Замени ту же строку на `Название команды: Огонь`. Закоммить.
4. Влей `new-name` в `main`. Git объявит конфликт — так и задумано.
5. Реши конфликт: оставь в файле то название, которое нравится больше (или придумай третье), убери маркеры, заверши слияние.

Проверка: `git log --oneline` показывает коммит слияния, а `cat team.txt` — чистый файл без единого символа `<` или `>`.

<details>
<summary>Решение (сначала попробуй сам)</summary>

```bash
mkdir team
cd team
git init
echo "Название команды: пока думаем" > team.txt
git add team.txt
git commit -m "начальное название"

git switch -c new-name
echo "Название команды: Молния" > team.txt
git commit -am "вариант Молния"

git switch main
echo "Название команды: Огонь" > team.txt
git commit -am "вариант Огонь"

git merge new-name
# CONFLICT (content): Merge conflict in team.txt
```

Теперь открой `team.txt` в редакторе (например, `nano team.txt`) — внутри будет:

```text
<<<<<<< HEAD
Название команды: Огонь
=======
Название команды: Молния
>>>>>>> new-name
```

Оставь одну строку, например `Название команды: Огненная Молния`, удали три строки с маркерами, сохрани файл и заверши слияние:

```bash
git add team.txt
git commit -m "решили конфликт: объединили названия"
git log --oneline
```

</details>

## Что должен уметь

- Объяснять, что такое ветка (branch), и почему её создание не копирует файлы проекта.
- Создавать ветку и переключаться между ветками через `git switch` — и узнавать ту же операцию в старой записи `git checkout`.
- Вливать ветку в `main` через `git merge` и объяснять разницу между перемоткой (fast-forward) и коммитом слияния (merge commit).
- Читать разметку конфликта: показывать, где чья версия и что означает каждый маркер.
- Решать конфликт до конца: выбрать текст, убрать маркеры, `git add`, `git commit`.
