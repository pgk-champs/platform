# Git: первый коммит

## Зачем это нужно

Представь: ты три часа доводил проект до рабочего состояния, потом «немного улучшил» — и всё сломалось. Как вернуть версию, которая работала? Копии `project_final_2_НОВЫЙ` в соседней папке — путь к хаосу. Для этого придумали систему контроля версий (version control system) — программу, которая запоминает состояния проекта в виде цепочки снимков. Самая распространённая такая система — Git. Каждый снимок называется коммитом (commit): что изменилось, когда и зачем. Можно листать историю, сравнивать версии и откатываться к любой точке — как чекпоинты в игре.

На чемпионате «Профессионалы» без этого никуда: работу сдают через git-репозиторий, и эксперты видят историю коммитов — по ней понятно, как ты шёл к результату. Один гигантский коммит «всё сразу» в конце дня выглядит подозрительно, а ровная цепочка маленьких осмысленных шагов — как работа профессионала. Поэтому привычку коммитить понемногу и часто ставим с первого дня.

## Сквозной пример: проект с одним файлом

Открой терминал Ubuntu и создай папку проекта:

```bash
mkdir my-app
cd my-app
git init
```

`git init` превращает обычную папку в репозиторий (repository) — хранилище проекта вместе со всей его историей. Внешне ничего не изменилось, но внутри появилась скрытая папка `.git`, где Git будет держать снимки. Один раз на компьютере нужно представиться — эти имя и почта будут подписью под твоими коммитами:

```bash
git config --global user.name "Ivan Petrov"
git config --global user.email "ivan@example.com"
```

Теперь создай файл `main.py` с одной строчкой (в любом редакторе, хоть `nano main.py`):

```python
print("Привет, чемпионат!")
```

Спроси у Git, что происходит:

```bash
git status
```

```
On branch master
Untracked files:
  main.py
```

`git status` показывает состояние (status) проекта: первая строка говорит, что мы на ветке (branch) `master` — про ветки будет отдельная глава, пока просто узнавай это слово. Дальше главное: `main.py` — untracked, Git видит файл, но не следит за ним. Снимки не делаются сами: сначала нужно сказать, что именно попадёт в следующий коммит.

```bash
git add main.py
```

`git add` кладёт файл в индекс (stage) — «корзину» для следующего снимка. Это удобно: изменил пять файлов, а в коммит положил два связанных — остальные подождут своего коммита. Теперь сам снимок:

```bash
git commit -m "add main screen"
```

Готово — первый коммит! Изменим файл: допиши в `main.py` вторую строчку, любую. Снова `git status` — файл теперь `modified` (изменён, но изменения ещё не в корзине). Цикл повторяется: `git add main.py`, потом `git commit -m "..."`. А посмотреть всю цепочку можно так:

```bash
git log --oneline
```

```
a1b2c3d add welcome message
f4e5d6c add main screen
```

`git log` показывает историю (history) — все коммиты от свежего к первому. Весь Git на базовом уровне — это цикл: **поменял файлы → `status` → `add` → `commit` → снова поменял**.

## Хорошие сообщения коммитов

Сообщение — это письмо себе и команде: через неделю по `git log` нужно понять, что происходило. Мировая привычка — писать по-английски, по формуле **глагол + что сделано**: `add login form`, `fix score reset`, `remove unused file`, `update readme`. Глагол — в начальной форме, как приказ: «добавь», «почини». Плохие сообщения: `fix`, `asdf`, `изменения 2`, `последняя версия точно` — через неделю они не скажут ничего. Хватает 3–6 слов, зато честных.

## .gitignore: что в историю не берём

Не всё в папке проекта заслуживает места в истории: временные файлы, логи, кэш вроде `__pycache__` — мусор, который создаётся сам. Чтобы `git status` не мозолил ими глаза, в корне проекта создают файл с именем `.gitignore` и перечисляют в нём, что игнорировать — по одному шаблону на строку:

```
__pycache__/
*.log
draft.txt
```

Звёздочка означает «любое имя»: `*.log` закрывает сразу все файлы логов. Сам `.gitignore` — обычный файл, его как раз коммитят, чтобы правила действовали у всей команды.

<summary>Углубиться</summary>

**Коммит — не «сохранение файла».** Git хранит не отдельные файлы, а снимки всего проекта целиком, и каждый коммит знает своего родителя — предыдущий коммит. Так и получается цепочка, по которой можно ходить назад. Длинная строка вроде `a1b2c3d` в `git log` — это хеш (hash), уникальный отпечаток коммита: по нему Git находит любой снимок за мгновение.

**Три состояния файла.** Git различает рабочую папку (working directory — где ты правишь файлы), индекс (staging area — что отобрано в следующий снимок) и саму историю. `git add` двигает изменения из первой во вторую, `git commit` — из второй в третью. Когда `git status` перестанет удивлять, значит, эта тройка уложилась в голове.

**`git add .`** — точка означает «всё из текущей папки». Удобно, но коварно: в коммит залетает всё подряд, включая случайный мусор. Пока учишься, добавляй файлы по именам — заодно будешь глазами видеть, что кладёшь в снимок.

## Челлендж ⭐

Продолжи проект `my-app` из главы серией из трёх коммитов — каждый решает одну задачу и подписан по-английски по формуле «глагол + что»:

1. Допиши в `main.py` строку, которая спрашивает имя пользователя. Закоммить.
2. Создай в папке черновик `draft.txt` и добейся, чтобы `git status` перестал его показывать. То, что для этого понадобилось, — закоммить.
3. Исправь текст приветствия в первой строке `main.py`. Закоммить.

Проверка: `git log --oneline` показывает минимум четыре коммита (три новых плюс `add main screen`), `git status` отвечает `nothing to commit, working tree clean` — при этом `draft.txt` спокойно лежит в папке.

<details>
<summary>Решение (сначала попробуй сам)</summary>

```bash
# 1. дописали в main.py строку input("Как тебя зовут? ")
git add main.py
git commit -m "add name question"

# 2. создали draft.txt, затем .gitignore со строкой draft.txt
git status            # draft.txt исчез из списка, .gitignore появился
git add .gitignore
git commit -m "add gitignore for drafts"

# 3. поправили текст в print(...)
git add main.py
git commit -m "fix greeting text"

git log --oneline     # четыре строки
```

Обрати внимание на второй шаг: коммитим именно `.gitignore`, а не черновик — сам `draft.txt` в историю не попадает никогда.

</details>

## Что должен уметь

- Объяснять своими словами, что такое репозиторий (repository), коммит (commit) и зачем проекту история.
- Прогонять полный цикл `git init` → `git status` → `git add` → `git commit -m "..."` → `git log` без подсказок.
- Читать вывод `git status`: отличать untracked-файл от modified и понимать, что уже лежит в индексе (stage).
- Писать сообщение коммита по-английски по формуле «глагол + что сделано» — коротким и честным.
- Прятать мусорные файлы от Git через `.gitignore` и объяснять, почему сам `.gitignore` при этом коммитят.
