# GitHub с нуля: регистрация и первые шаги

<ChapterProgress chapterId="github-start" totalSections={15} totalQuizzes={6} totalTrainers={1} />

Эта страница — для человека, который с компьютером пока на «вы». Здесь нет ни одной команды и ни одной строчки кода: только как завести себе аккаунт на GitHub, войти в него, принять приглашение наставника и отправить свою первую заявку. Каждый экран описан словами — что на нём написано, куда нажать и какие ошибки бывают. Если что-то на твоём экране выглядит чуть иначе — это нормально: GitHub время от времени переставляет кнопки, но смысл шагов не меняется.

<Fold title="Совсем новичок в компьютере? Открой сначала это">

Если раньше почти не пользовался компьютером — вот три вещи, без которых регистрация и работа с почтой будут даваться труднее, чем должны. Остальное в главе рассчитано и на тебя, просто эти три пригодятся уже на первом шаге.

**Вкладки браузера.** Вверху окна браузера — полоска с «ярлычками»-вкладками: каждая открывает свою страницу, а всё окно можно не закрывать. Новая вкладка — значок `+` рядом с последней или сочетание `Ctrl+T` (`Cmd+T` на macOS). Переключаться между вкладками — просто кликнуть по нужной. Закрыть вкладку — крестик на ней или `Ctrl+W`. Это пригодится буквально в этой же главе: открыть почту в соседней вкладке, не теряя страницу GitHub с формой регистрации.

**Поиск письма в почте.** Когда писем много, листать их все не нужно — вверху страницы почты есть строка поиска. Кликни в неё и напечатай слово из письма, которое ищешь, — например `GitHub`. Почтовый сервис сам покажет только подходящие письма, обычно самое новое — сверху.

**Копирование ссылки.** Ссылка (link) — это адрес страницы, обычно синего цвета и подчёркнутый или начинающийся с `https://`. Скопировать её текстом можно так же, как любой текст: выделить и нажать `Ctrl+C` (`Cmd+C` на macOS). Потренироваться можно сразу под этим блоком — в тренажёре «Выдели и скопируй ссылку»: там адрес показан текстом, и его нужно выделить целиком (двойной клик выделит только одно слово из него, а нужен адрес целиком — подойдёт протяжка мышью или тройной клик по всей строке).

**Куда дальше**, если хочется потренировать базовые навыки компьютера ещё подробнее и не спеша:

- [neumeka.ru](https://neumeka.ru/) — бесплатные русскоязычные уроки компьютерной грамотности с нуля: мышь, клавиатура, файлы, интернет.
- [Northstar Digital Literacy](https://www.digitalliteracyassessment.org/build-skills) — бесплатный англоязычный курс с самопроверкой по темам: базовые навыки компьютера, интернета, работы с файлами.

</Fold>

## Без чего не обходится ни один настоящий проект

Прежде чем регистрироваться, стоит понять, зачем всё это вообще нужно — иначе GitHub покажется просто ещё одним сайтом с логином и паролем. Представь на секунду курсовую или диплом без всякого Git: пишешь текст, сохраняешь файл `diplom.docx`. На следующий день добавляешь главу — на всякий случай сохраняешь копию рядом, `diplom_v2.docx`. Научный руководитель просит исправить абзац — правишь, но вдруг зря, поэтому ещё одна копия: `diplom_v2_ИСПРАВЛЕНО.docx`. Через месяц таких файлов на рабочем столе полтора десятка, и ни один не подписан внятно: непонятно, какой правда последний, что именно менялось между `_ИСПРАВЛЕНО` и `_ИСПРАВЛЕНО_2`, а один файл вообще случайно затёрли, сохранив поверх старую версию под новым именем. Знакомая картина — и с кодом происходит буквально то же самое, только хуже: код меняют по многу раз в день, часто несколько человек одновременно, и любая перезаписанная без следа версия — это не абзац текста, а рабочая программа, которая внезапно перестала запускаться, а никто не помнит, что именно её сломало.

Git — программа, которая решает ровно эту задачу: вместо кучи файлов с именами-«версиями» она хранит одну папку с проектом и полную историю изменений внутри неё. Каждое сохранение (в Git это называется коммит — подробно разберём его в главах про Git) — это не новая копия файла, а отметка «вот что изменилось, кто это сделал и когда» с текстовым объяснением: «поправил формулу в разделе 3», «добавил тесты для авторизации». Вернуться к любому прежнему состоянию, посмотреть, кто что менял, и понять, из-за какого именно изменения всё сломалось, — то, ради чего Git вообще существует. Придумал его в 2005 году Линус Торвальдс — тот же человек, что создал ядро Linux, — потому что над самим ядром одновременно работали тысячи разработчиков по всему миру, и без такого инструмента их правки было бы просто невозможно свести воедино.

## Git и GitHub — не одно и то же

Тут важно не перепутать два похожих слова, которые всё время стоят рядом. Git — это программа, движок версий: она умеет запоминать историю изменений и работает прямо на твоём компьютере, даже без интернета — примерно как Word умеет сохранять документ на диск без всякой сети. GitHub — сайт, который хранит копии таких Git-репозиториев в интернете и добавляет вокруг них инструменты для командной работы: страницу с файлами прямо в браузере, issue для обсуждений, кнопку Fork, автоматические проверки (Actions) — обо всём этом дальше и пойдёт речь. Аналогия попроще: Git — это сам Word, программа для работы с документом; GitHub — что-то вроде общей папки в интернете, куда документ выкладывают, чтобы к нему был доступ у всей команды, с историей правок и обсуждением поверх.

GitHub — не единственный сайт такого рода: у него есть похожие по смыслу аналоги, GitLab и Bitbucket, — просто в мире учебных и рабочих проектов GitHub самый распространённый, и весь этот курс построен вокруг него. Программу Git на компьютер мы пока не ставили — с этого не начинают, если человек прежде вообще не открывал терминал; этим займётся одна из следующих глав фундамента. Всё, что происходит в этой главе, — работа в браузере, на сайте GitHub, без единой команды.

## Что такое аккаунт и зачем ему почта

GitHub (читается «гит-ха́б») — это сайт, где программисты всего мира хранят свой код и работают над ним вместе. Для нас он будет рабочим местом: там лежат задания практикумов, туда отправляются решения, там наставник видит твой прогресс.

<Figure img="/img/photos/laptop-code.jpg" alt="Руки над клавиатурой ноутбука, на экране — код" caption="GitHub — место, где живёт код: сюда ты будешь отправлять работы и получать отклик наставника." source="Фото: Pexels, pexels.com/photo/574071 — свободная лицензия Pexels, атрибуция не требуется" />

**Аккаунт** — это твоя личная учётная запись на сайте: имя, пароль и всё, что ты на сайте сделал. Примерно как аккаунт в соцсети или в Госуслугах, только для кода. Чтобы сайт знал, что ты — это ты, при регистрации нужны две вещи:

- **Электронная почта** — ящик вида `имя@mail.ru` или `имя@gmail.com`. На него GitHub пришлёт код подтверждения, а потом будет присылать уведомления. Подойдёт любая почта, которой ты реально пользуешься и от которой помнишь пароль. Если почты нет совсем — заведи её сначала (на любом крупном сервисе), это отдельные десять минут.
- **Пароль** — секретное слово, которое знаешь только ты. Не тот же, что от почты: для каждого сайта — свой.

<Hint id="gh-start-password-safety" type="important">
Пароль от GitHub не говори и не пересылай никому — ни одногруппнику, ни «техподдержке» из письма. Настоящий GitHub никогда не спрашивает пароль в письмах. Наставнику твой пароль тоже не нужен: для совместной работы есть приглашения в организацию, о них ниже. Запиши пароль в надёжное место — в менеджер паролей или в бумажный блокнот, который лежит дома, а не в файл «пароли.txt» на рабочем столе.
</Hint>

## Регистрация по шагам

Открой в браузере адрес `github.com`. В правом верхнем углу будет кнопка **Sign up** («зарегистрироваться»). Нажми её — попадёшь на страницу регистрации `github.com/signup`. Если увидишь там кнопку **Continue with Google** — это вход через Google-аккаунт: рабочий вариант, если у тебя почта Gmail. Но мы пройдём обычный путь с формой — он работает с любой почтой. Дальше — по одному полю за раз.

<Figure scheme="gh-signup-flow" caption="Регистрация по шагам: почта, пароль, логин, код с почты — и аккаунт готов." />

**Шаг 1. Email.** Поле подписано «Email». Введи свою почту целиком, с собачкой и точкой: `ivanov2008@mail.ru`. Частые ошибки: опечатка (лишняя буква, запятая вместо точки) — тогда код подтверждения просто не дойдёт; или сообщение «email is invalid or already taken» — «почта неверна или уже занята». «Занята» означает, что на эту почту уже когда-то заводили аккаунт GitHub — возможно, ты сам и забыл. Тогда не регистрируйся заново, а попробуй войти (раздел «Вход» ниже) и восстановить пароль.

**Шаг 2. Password (пароль).** Придумай новый пароль. Требование GitHub: либо не короче 15 любых символов, либо не короче 8, но тогда обязательно с цифрой и маленькой латинской буквой. Надёжный и лёгкий для запоминания вариант — три несвязанных слова латиницей плюс цифры: `sobaka9velosiped2zima`. Пока требования не выполнены, форма подсвечивает, чего не хватает, и дальше не пускает.

**Шаг 3. Username (логин, имя пользователя).** Это твоё публичное имя на GitHub — оно будет видно всем и станет частью адреса твоей странички: `github.com/твой-логин`. Разрешены только латинские буквы, цифры и дефис; начинаться и заканчиваться дефисом нельзя, длина — до 39 символов. Русские буквы, пробелы и точки не подойдут. Если логин занят, GitHub скажет «Username is not available» и предложит свободные варианты — можно взять один из них или дописать цифры.

<Hint id="gh-start-username-tip" type="tip">
Логин выбирай так, чтобы не стыдно было показать работодателю через пять лет: GitHub-профиль у программистов часто спрашивают вместо портфолио. `ivan-petrov` или `ipetrov-dev` состарятся лучше, чем `killer2008xxx`. Поменять логин потом можно, но все старые ссылки на твой профиль перестанут работать.
</Hint>

**Шаг 4. Страна и рассылка.** В поле «Country/Region» выбери из списка свою страну. Если предлагают галочку про новости и предложения по почте («Email preferences») — можно не ставить, на работу это не влияет.

**Шаг 5. Проверка «ты не робот».** GitHub покажет мини-головоломку — например, повернуть картинку в правильное положение или выбрать подходящую фигуру. Задание описано по-английски, но обычно понятно и без слов. Это защита от программ, которые заводят фальшивые аккаунты. Не получилось с первого раза — ничего страшного, дадут ещё попытку.

**Шаг 6. Код с почты (launch code).** GitHub отправит на указанную почту письмо с кодом из восьми цифр — в письме он называется «launch code». Открой почту в соседней вкладке, найди письмо от GitHub, перепиши код в поле на странице регистрации. Письма нет две-три минуты? Загляни в папку «Спам» — оно любит падать туда. Совсем нет — на странице есть кнопка повторной отправки (Resend).

**Шаг 7. Вопросы и тариф.** После подтверждения GitHub может позадавать вопросы: сколько опыта, для чего аккаунт, сколько человек в команде. Это не экзамен — отвечай как угодно или ищи ссылку «Skip» («пропустить»). Если предложат выбрать тариф — жми вариант **Free** (бесплатный) или «Continue for free». Всё, что нужно для учёбы и практикумов, в бесплатном тарифе есть; платить не нужно ничего и никогда в рамках нашего курса.

Готово: ты на главной странице своего аккаунта. Выглядит пустовато — так и должно быть, наполнять начнём с первого практикума.

## Вход и выход

Регистрируются один раз, а входят — постоянно, поэтому запомни дорогу. На `github.com` в правом верхнем углу есть кнопка **Sign in** («войти»). Она спросит две вещи: «Username or email address» — логин или почту, без разницы, и «Password» — пароль. Дальше кнопка **Sign in**.

Забыл пароль — не беда и не стыдно: под формой есть ссылка **Forgot password?** («забыли пароль?»). Введёшь почту — придёт письмо со ссылкой для смены пароля. Именно поэтому важно регистрироваться на почту, в которую ты умеешь заходить.

Выход — по клику на свой кружок-аватарку в правом верхнем углу: в выпавшем меню внизу есть **Sign out**. На своём личном компьютере можно не выходить вовсе; на чужом или общем (в колледже!) — выходи обязательно.

## Аватарка и имя: чтобы тебя узнавали

Свежий аккаунт получает случайную пиксельную картинку-заглушку. Наставнику куда проще, когда в списке из двадцати студентов видно живые лица или хотя бы осмысленные картинки, а не двадцать одинаковых пикселей.

Кликни на свой кружок в правом верхнем углу и выбери в меню пункт **Settings** («настройки»). Откроется страница профиля — раздел **Public profile**. Справа будет твоя текущая картинка и кнопка **Edit** (или сразу **Upload a photo…** — «загрузить фото»). Нажми, выбери файл с картинкой на компьютере, при желании подвинь рамку кадрирования и подтверди. Тут же, в поле **Name**, можно вписать имя и фамилию — можно по-русски: логин останется латиницей, а имя будет отображаться человеческое. Изменения сохраняются кнопкой **Update profile** внизу.

## Принять приглашение в организацию

**Организация** на GitHub — это общий «кабинет» команды: набор репозиториев (репозиторий — «папка с проектом» на GitHub; подробно про них — в главах про Git) и список участников. У нас она называется `pgk-champs` — там живут задания, каталог сообщества и таблица результатов. Самому в организацию не вступить: наставник отправляет **приглашение** (invitation) на твой логин или почту — скажи ему логин, который выбрал при регистрации.

Приглашения бывают двух видов, и от наставника может прийти любое — оба принимаются в один клик:

- **в саму организацию** — тебя добавляют в команду `pgk-champs` целиком;
- **в отдельный репозиторий** — тебя делают соавтором (collaborator) конкретной «папки с проектом» — например, своего личного репозитория практикума `pgk-champs/sprint1-<твой-логин>`. Письмо тогда называется иначе: «…invited you to collaborate on pgk-champs/sprint1-…», и внутри — зелёная кнопка **Accept invitation** («принять приглашение»). Плашки на `github.com/pgk-champs` в этом случае не будет и значок организации в профиле не появится — это нормально: доступ выдан к репозиторию, а не ко всему кабинету. После нажатия откроется сам репозиторий — сохрани ссылку на него, она пригодится в главе про Git.

<Figure scheme="gh-invite-paths" caption="Два вида приглашения: в организацию — видно все репозитории; в отдельный репозиторий — доступ только к нему." />

Разберём подробно первый вид — приглашение в организацию. Тут два пути, оба простые:

1. **Через письмо.** На почту придёт письмо от GitHub со словами вроде «You've been invited to join the pgk-champs organization» — «вас пригласили в организацию». Внутри — большая кнопка **Join** или ссылка **View invitation** («посмотреть приглашение»). Нажми её: откроется страница GitHub (войди, если попросит) с зелёной кнопкой **Join pgk-champs**. Нажал — ты в команде.
2. **Без письма.** Войди на GitHub и открой адрес `github.com/pgk-champs` — если приглашение ждёт тебя, сверху страницы будет плашка с тем же предложением присоединиться.

Приглашение живёт около недели. Протянул и оно «протухло» — ничего страшного: попроси наставника отправить новое.

Проверить, что всё получилось, просто: на странице `github.com/pgk-champs` ты теперь видишь репозитории организации, а на своей страничке профиля появился её значок. Если приглашение было в отдельный репозиторий, проверка другая: открой `github.com/<твой-логин>?tab=repositories` — репозиторий, к которому дали доступ, будет в этом списке; либо просто перейди по ссылке из письма, она ведёт прямо в него.

Ни в том, ни в другом случае от тебя не потребуется ни пароля, ни оплаты. Любое письмо «подтвердите пароль, чтобы принять приглашение» — не от GitHub; настоящее приглашение принимается кнопкой на самом сайте, куда ты уже вошёл.

## Что реально лежит внутри репозитория

Слово «репозиторий» уже несколько раз мелькало выше как «папка с проектом» — разберём подробнее, что это значит на практике. Открой любой публичный репозиторий, например один из проектов внутри `github.com/pgk-champs`, и посмотри на страницу: сверху список файлов и папок — ровно то же самое, что видно в проводнике на компьютере, только в браузере. Каждый файл кликабелен и открывается с подсветкой кода. Рядом — переключатель ветки (branch), обычно там написано `main`: подробно об этом расскажут главы про Git, а пока достаточно знать, что это «основная», рабочая версия проекта. Под списком файлов GitHub сам, автоматически, показывает содержимое файла `README.md`, если он есть, — про него отдельный разговор ниже.

Ещё на странице репозитория обычно есть блок **About** — короткое описание, чем проект занимается, ссылка на сайт, если есть, и облако тегов-тем (topics), по которым проект находят через поиск. Число рядом со словом **Commits** — сколько раз в этот репозиторий что-то сохраняли за всю историю; у активного проекта это могут быть тысячи. А за всем этим — невидимая на первый взгляд служебная папка `.git`, в которой Git и хранит всю историю: она не показывается в обычном списке файлов ни на GitHub, ни в проводнике по умолчанию, потому что предназначена не для чтения человеком, а для самого Git — трогать её руками не придётся никогда.

## README: то, что репозиторий рассказывает о себе сам

`README.md` — файл, который GitHub привилегирует особо: как только он есть в корне репозитория, сайт сам показывает его содержимое прямо под списком файлов — первое, что видит любой человек, открывший репозиторий, ещё до того, как разберётся в остальном коде. Название важно набрать точно: заглавными буквами `README` и с расширением `.md` (markdown — лёгкая разметка текста: `#` перед строкой делает заголовок, `-` в начале строки — пункт списка, текст в обратных кавычках оформляется как код). Разбирать markdown подробно эта глава не будет — важнее другое: зачем README вообще нужен.

У опытного разработчика привычка простая: не бывает нормального репозитория без внятного README. Хороший README отвечает на вопросы, которые задаст любой, кто впервые открыл проект: что это вообще такое, одной строкой; как его запустить у себя; какие есть команды или ссылки; кто автор и по какой лицензии можно пользоваться кодом. Пустой репозиторий без единого файла GitHub сам подсказывает завести README первым — недаром: без него даже автор через полгода может не вспомнить, что за проект он вообще написал и как его запускали. Дальше в курсе появятся репозитории собственных практикумов и портфолио — привычку писать README для них стоит выработать сразу, а не откладывать «на потом», которое обычно не наступает.

<Hint id="gh-start-readme-min" type="tip">
Даже одна строка — уже лучше, чем пустой README: `# Приложение погоды на Kotlin — показывает прогноз по городу через открытое API` уже отвечает на главный вопрос «что это». Оформлять README подробнее — с разделами про установку и запуск — научит одна из следующих глав курса.
</Hint>

## Публичный или приватный: кто увидит твой репозиторий

У каждого репозитория на GitHub есть один из двух режимов видимости, и выбирают его в момент создания (создавать репозитории своими руками курс научит в главах про Git — здесь пока только суть на будущее). **Public** («публичный») — репозиторий открыт для чтения кому угодно в интернете, даже без аккаунта GitHub: любой найдёт его через поиск, откроет файлы, скопирует код себе. **Private** («приватный») — видят и открывают только те, кого явно пригласили соавтором; для всех остальных такого репозитория как будто не существует вовсе, даже в поиске он не покажется.

Именно поэтому личные практикумы `pgk-champs/sprint1-<твой-логин>`, о которых шла речь выше, наставник всегда создаёт приватными: чтобы решение одного студента не увидел другой раньше дедлайна. А вот когда дело дойдёт до собственного портфолио — личных проектов, которые показывают будущим работодателям, — обычно выбирают ровно противоположное, Public: чтобы код мог посмотреть кто угодно, в этом и смысл открытого портфолио. Изменить видимость можно и постфактум, в Settings репозитория, но с оговоркой: если в приватном репозитории случайно оказался чужой пароль или ключ доступа, простое переключение на Public эту утечку не отменяет — история коммитов, где секрет засветился, никуда не девается вместе со сменой видимости. К темам вроде «что делать, если случайно закоммитил пароль» вернёмся куда подробнее в главах про Git; здесь достаточно запомнить одно практическое правило: секреты (пароли, ключи API) не кладут в репозиторий вообще, ни в публичный, ни в приватный. Бесплатный аккаунт GitHub, кстати, разрешает неограниченное число приватных репозиториев — ограничения тарифа этого не касаются.

## Получить чужой код: форк и клонирование на пальцах

Ещё одна пара слов, которую в первые недели почти все путают, — форк (fork) и клонирование (clone). Путаница понятна: оба про «взять чужой репозиторий себе», но происходит это в двух разных местах и по разным причинам.

**Клонирование** — это скачать репозиторий с GitHub к себе на компьютер, со всеми файлами и всей историей разом; выполняется командой Git (`git clone`) и подробно разберём её в одной из следующих глав. Копия появляется только локально, на диске, — если у тебя нет права на запись в исходный репозиторий, отправить туда изменения обратно так просто не получится.

**Форк** — действие не Git, а самого GitHub: кнопка **Fork** в правом верхнем углу страницы репозитория создаёт твою личную копию этого репозитория прямо на сайте, под твоим аккаунтом (`github.com/твой-логин/название-проекта`) — и вот в неё у тебя уже есть полное право писать, потому что теперь это формально твой собственный репозиторий. Форк используют, когда хочется доработать или изучить чужой открытый проект, в который у тебя изначально нет доступа на запись, — типичный случай для любого открытого кода в интернете.

<Figure scheme="clone-vs-fork" caption="git clone копирует чужой репозиторий сразу на диск; Fork сначала создаёт твою копию на GitHub, и уже её можно клонировать себе — так к своей копии открывается полный доступ на запись." />

На практике оба приёма часто соединяют: сначала жмут Fork, чтобы получить свою копию на GitHub, а затем эту свою копию уже клонируют себе на компьютер, — но для практикумов этого курса ни то, ни другое пока не понадобится: репозиторий для каждого спринта наставник создаёт лично и сразу выдаёт право на запись, форкать шаблон «на всякий случай» не нужно. Пригодится это на командной работе и при взгляде на чужие открытые проекты — со всеми подробностями, включая саму команду `git clone`, доразберёмся в главе «[Git: push, PR и командная работа](/docs/foundation/git-remote)».

## Открыть issue по ссылке и нажать Submit

**Issue** (читается «и́шью», по-русски часто «ишью́шка» или просто «заявка») — это карточка-обращение в репозитории: вопрос, предложение или заявка на что-то. У нас через issue устроена, например, отправка материалов в каталог сообщества и сдача результатов: наставник даёт ссылку, ты заполняешь форму — и всё.

Как это выглядит по шагам:

1. Наставник присылает ссылку (в чат группы или лично). Открой её в браузере — если попросит, войди в GitHub.
2. Откроется **форма** — анкета с полями: где-то нужно выбрать вариант из списка, где-то вписать текст. Обязательные поля помечены красной звёздочкой; пока они пустые, форма не отправится.
3. Заполни поля по инструкции наставника (или по гайду, если это заявка в каталог сообщества).
4. Внизу — зелёная кнопка **Submit new issue** («отправить»). Нажми её один раз и подожди: страница перезагрузится сама.
5. После отправки откроется страница твоего issue — у него будет номер вида `#42` и твой заголовок. Это нормально и правильно: заявка создана, её видят наставник и роботы.
6. Когда на заявку ответят (комментарием под ней), тебе придёт письмо на почту, а на GitHub загорится колокольчик уведомлений в правом верхнем углу.

Найти свои старые заявки можно так: на любой странице GitHub вверху есть поиск и меню — открой `github.com/issues`, там список «Created» — всё, что создал ты.

## «Зелёная галочка»: как понять, что практикум сдан

В практикумах платформы работу проверяет не человек, а робот — GitHub Actions. Как только ты отправляешь своё решение в репозиторий (этому научит глава про Git), робот запускает проверку: собирает проект и гоняет тесты. Результат он показывает значком рядом с твоей последней отправкой и во вкладке **Actions** репозитория:

<Figure scheme="gh-check-states" caption="Три значка проверки в Actions: зелёная галочка — сдано, красный крестик — есть проблема, жёлтая точка — проверка идёт." />

- **Зелёная галочка ✓** — все проверки прошли. Для практикума это и есть «сдано»: «сдано = зелёная галочка» написано прямо в задании.
- **Красный крестик ✗** — что-то не прошло. Это не «двойка», а подсказка: кликни по крестику — откроется журнал проверки, где видно, какой именно тест упал.
- **Жёлтая точка ●** — проверка ещё идёт, подожди минуту-другую и обнови страницу.

Пока просто запомни, где смотреть: вкладка **Actions** сверху страницы репозитория, самая верхняя строчка списка — последняя проверка. Как отправлять решения, чтобы эта галочка появилась, разберут главы про Git — начиная с «[Git: первый коммит](/docs/foundation/git-first-commit)».

<Hint id="gh-start-octocat" type="fact">
GitHub появился в 2008 году, а сегодня на нём больше ста миллионов аккаунтов — почти все программисты мира. Талисман сайта — Октокот (Octocat), кот с щупальцами осьминога. Так что аккаунт, который ты только что завёл, — тот же самый инструмент, которым пользуются авторы Linux, Android и почти всех программ у тебя в телефоне.
</Hint>

## Частые путаницы первого дня

Под конец — короткий список того, что почти у всех вызывает заминку в первую неделю на GitHub. Ничего страшного тут нет, но лучше знать заранее, чем спотыкаться вживую.

- **Путать Git и GitHub.** Уже разобрали подробно выше, но путаница цепкая: если что-то «не работает в Git», а на самом деле ты сидишь в браузере на сайте GitHub, — стоит сначала понять, о какой из двух вещей вообще речь.
- **Заводить второй аккаунт вместо входа в старый.** Забыл логин или пароль — первым делом пробуй **Forgot password?**, а не регистрацию заново: два аккаунта на одного человека только всё запутывают, а наставник ждёт приглашения на конкретный, единственный логин.
- **Входить на общем компьютере и забывать выйти.** Особенно в компьютерном классе колледжа: следующий человек за той же машиной случайно окажется «залогинен» под твоим именем. Про `Sign out` уже говорили выше — привычка выходить на чужих устройствах должна стать рефлексом.
- **Не заполнять имя и аватар в Settings.** Формально ничего не сломается, но наставник, ищущий тебя среди двадцати одинаковых пиксельных заглушек, потратит на это лишнее время — раздел выше про аватарку не просто «для красоты».
- **Считать, что Fork нужен для любого чужого репозитория.** Если тебе уже выдали право записи (как в практикумах этого курса) — форк не нужен вовсе, обычного клонирования достаточно; кнопка Fork нужна только там, где своего доступа на запись нет и не будет.

<Hint id="gh-start-2fa" type="important">
GitHub время от времени предлагает включить двухфакторную аутентификацию (2FA) — вход не только по паролю, но и по коду из приложения на телефоне. Включать её на первой неделе не обязательно, но если решишься — сайт один раз покажет **recovery codes**, резервные коды на случай утери телефона. Их обязательно сохраняют не на самом телефоне (потеряется вместе с ним), а отдельно, например в менеджере паролей: без пароля восстановить доступ можно через почту, а вот без recovery codes при потерянном телефоне с включённой 2FA — по-настоящему сложно.
</Hint>
