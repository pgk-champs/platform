# Git: push, PR и командная работа

## Зачем это нужно

Пока твой репозиторий живёт только на твоём компьютере, у него две проблемы. Первая — надёжность: умер диск, пролили чай на ноутбук — и вся история коммитов исчезла вместе с кодом. Вторая — одиночество: напарник по команде не может ни посмотреть твой код, ни добавить свой. Обе проблемы решает удалённый репозиторий (remote) — копия твоего репозитория на сервере в интернете, с которой локальный репозиторий умеет синхронизироваться.

Для тебя это не абстракция: на чемпионате «Профессионалы» и в практикумах платформы сдача работы — это отправка коммитов на сервер. Пока код лежит только у тебя, для проверяющих задания не существует. А в командных модулях через общий удалённый репозиторий идёт вся работа: каждый пишет у себя, отправляет наверх и забирает то, что отправили остальные.

## GitHub и четыре команды

GitHub — самый популярный сайт, где живут удалённые репозитории. Он хранит код, показывает историю коммитов прямо в браузере и добавляет инструменты командной работы — главный из них, pull request, разберём чуть ниже. У локального репозитория может быть несколько remote, но обычно он один, и по традиции его зовут `origin`.

Связь с удалённым репозиторием держится на трёх командах:

- **Клонировать (clone)** — `git clone <адрес>` скачивает удалённый репозиторий целиком: код, все ветки и всю историю коммитов. Заодно Git сам прописывает адрес как `origin`. Так начинается работа над любым существующим проектом — клонировал и пишешь.
- **Отправить (push)** — `git push` загружает твои локальные коммиты на сервер. Коммит без push — как письмо без «отправить»: написано, но никто не прочитает.
- **Забрать (pull)** — `git pull` скачивает коммиты, которые появились на сервере (например, их отправил напарник), и вливает их в твою локальную ветку. Правило командной работы: перед началом дня — pull, в конце куска работы — push.

## Pull Request: код проверяют до слияния

В командах не принято отправлять коммиты прямо в главную ветку `main` — один неудачный коммит сломал бы проект всем сразу. Вместо этого работу делают в отдельной ветке, отправляют её на сервер и открывают запрос на слияние (pull request, PR) — предложение «влейте мою ветку в main». Это не команда Git, а кнопка на GitHub.

В открытом PR команда видит все твои изменения строка за строкой, может комментировать конкретные места и просить поправить. Такой разбор кода называется ревью (review). Когда замечания исправлены и PR одобрен, одна кнопка вливает ветку в `main`. В практикумах платформы наставник смотрит твою работу именно так — поэтому аккуратная ветка и понятные сообщения коммитов работают на твою оценку.

## rebase и cherry-pick: осторожно, история

Две команды, о которых стоит знать заранее, — их часто советуют в интернете, не предупреждая о последствиях.

Перебазирование (rebase) — `git rebase main` — переставляет коммиты твоей ветки на свежий конец `main`, будто ты начал работу позже. История становится линейной, без узлов слияния. Cherry-pick — `git cherry-pick <коммит>` — переносит один конкретный коммит из другой ветки в твою: удобно, когда нужна ровно одна правка, а не вся ветка.

Обе команды не двигают старые коммиты, а создают новые копии с другими идентификаторами — то есть переписывают историю. Отсюда главное правило: **не переписывай то, что уже отправлено на сервер и есть у других людей**. Иначе у напарников останется старая версия истории, у тебя будет новая, и Git начнёт путаться в двух вариантах одних и тех же коммитов. Пока коммиты лежат только у тебя локально — rebase безопасен.

<details>
<summary>Углубиться</summary>

**pull = fetch + merge.** На самом деле `git pull` — это две операции подряд: `git fetch` скачивает новые коммиты с сервера, никуда их не вливая, а затем `git merge` вливает их в твою текущую ветку. Иногда полезно делать их раздельно: после `fetch` можно спокойно посмотреть, что изменилось, до того как это попадёт в твою ветку.

**Ветки-отражения.** После `fetch` в репозитории появляются ветки вида `origin/main` — локальные «фотографии» состояния сервера на момент последней синхронизации. Когда Git пишет «your branch is ahead of origin/main by 2 commits», он сравнивает твою ветку именно с такой фотографией: у тебя есть два коммита, которых сервер ещё не видел.

**Что именно делает `-u`.** Флаг записывает в конфиг репозитория upstream — связку «локальная ветка ↔ ветка на сервере». После этого `git push` и `git pull` без аргументов знают, куда отправлять и откуда забирать. Забыл флаг — не страшно: Git откажется пушить и сам подскажет полную команду с `-u`.

## Челлендж ⭐

Пройди полный путь «получил проект — сдал работу» на учебном шаблоне платформы.

1. Открой на GitHub репозиторий `track-mobile-01-kotlin-basics` в организации `pgk-champs` и нажми **Fork** — это создаст форк (fork), твою личную копию репозитория, в которую у тебя есть право пушить.
2. Клонируй **свой форк** (не оригинал!) на компьютер.
3. Создай ветку `feature/<твоя-фамилия>` латиницей.
4. Добавь в неё хотя бы один коммит — например, файл `about.txt` с твоим именем и группой.
5. Отправь ветку на сервер и убедись в браузере, что она появилась в твоём форке.

Бонус: открой pull request из своей ветки — GitHub сам предложит это жёлтой плашкой, как только увидит свежую ветку.

<details>
<summary>Решение (сначала попробуй сам)</summary>

После нажатия Fork на GitHub, в терминале (замени `<логин>` и фамилию на свои):

```bash
git clone https://github.com/<логин>/track-mobile-01-kotlin-basics.git
cd track-mobile-01-kotlin-basics
git switch -c feature/ivanov
echo "Иванов Иван, группа ИС-11" > about.txt
git add about.txt
git commit -m "Добавил файл о себе"
git push -u origin feature/ivanov
```

Затем открой страницу форка в браузере — ветка `feature/ivanov` должна быть в списке веток, а сверху появится предложение открыть pull request.

</details>

## Что должен уметь

- Объяснять, что такое удалённый репозиторий (remote), почему его обычно зовут `origin` и зачем нужен GitHub.
- Пользоваться тремя командами синхронизации: `git clone`, `git push`, `git pull` — и знать, когда какая нужна.
- Читать `git push -u origin feature/login` по частям и объяснять, что делает флаг `-u`.
- Описывать путь изменений в команде: отдельная ветка → push → pull request → ревью → слияние в `main`.
- Формулировать правило безопасности для rebase и cherry-pick: почему нельзя переписывать уже отправленную историю.
