# ООП простыми словами — на двух языках

<ChapterProgress chapterId="oop-basics" totalSections={18} totalQuizzes={5} totalTrainers={1} />

## Зачем это нужно

В главе [«Из чего состоит код»](/docs/foundation/code-basics) разобрано всё, из чего программа складывается физически: переменная, тип, вызов, аргумент, точка как доступ к члену, скобки. Этого достаточно, чтобы написать программу на двести строк. И ровно на двухсотой строке начинается проблема, которую никакая новая конструкция языка не решает: **данные и действия над ними разъезжаются**.

Выглядит это так. Есть переменные `studentName`, `studentGroup`, `studentAverage`. Есть функции `printStudent`, `updateAverage`, `isExpelled`. Каждая функция принимает три аргумента, потому что иначе она не знает, о ком речь. Появляется второй студент — переменных становится шесть. Появляется преподаватель — двенадцать. И вот уже половина кода занята тем, чтобы правильные значения попали в правильные функции в правильном порядке, а самая частая ошибка — передать `teacherName` туда, где ждали `studentName`. Компилятор не возражает: обе строки.

Объектно-ориентированное программирование (ООП) — это ответ ровно на эту боль: **сложить данные и действия над ними в одну коробку и дальше передавать коробку целиком**. Никакой философии, никаких «сущностей реального мира» — простое соображение об организации кода, которому уже полвека.

Эта глава — про базовый набор понятий ООП, и каждое из них показано сразу на двух языках: **Kotlin** (мобильный трек) и **TypeScript** (блокчейн-трек). Не потому что нужно знать оба, а потому что рядом видно главное: идея одна, запись разная. Тот, кто это увидел один раз, дальше читает чужой код на незнакомом языке в разы спокойнее.

## Как жили до объектов и почему перестали

Возьмём задачу из жизни колледжа: хранить студента и уметь его поприветствовать. Без всякого ООП, только переменные и функции.

```kotlin
// Kotlin — до объектов
var studentName = "Аня"
var studentGroup = "ИС-31"

fun greet(name: String, group: String): String {
    return "Привет, $name из группы $group"
}

println(greet(studentName, studentGroup))
```

```ts
// TypeScript — до объектов
let studentName = "Аня";
let studentGroup = "ИС-31";

function greet(name: string, group: string): string {
  return `Привет, ${name} из группы ${group}`;
}

console.log(greet(studentName, studentGroup));
```

Работает. Проблемы начинаются от третьей строки данных:

1. **Связь между переменными существует только в голове.** `studentName` и `studentGroup` относятся к одному человеку, но язык об этом не знает. Ничто не мешает передать имя одного студента и группу другого — программа спокойно напечатает несуществующего человека.
2. **Количество аргументов растёт.** Добавили средний балл, курс, номер зачётки — и `greet` принимает пять аргументов, а перепутать их местами стало ещё легче.
3. **Второй студент — это ещё один набор переменных.** `studentName2`, `studentGroup2`. Пятый — уже катастрофа, и обычно на этом месте человек сам изобретает массивы или словари.
4. **Непонятно, где искать код про студента.** Функции разбросаны по файлу вперемешку с функциями про всё остальное.

Первый шаг, который делают почти интуитивно, — сложить связанные данные в одну структуру:

```kotlin
// Kotlin: данные в одной коробке
val student = mapOf("name" to "Аня", "group" to "ИС-31")
println(greet(student["name"]!!, student["group"]!!))
```

```ts
// TypeScript: данные в одной коробке
const student = { name: "Аня", group: "ИС-31" };
console.log(greet(student.name, student.group));
```

Стало лучше: студент — одна переменная, передаётся целиком. Но `greet` по-прежнему живёт отдельно и по-прежнему принимает куски студента по отдельности. Осталось сделать последний шаг — положить в ту же коробку и действия. Коробка с данными и действиями называется **объектом**.

<Hint id="oop-basics-h1" type="fact">
Слово «объект» звучит абстрактно, но исторически всё было приземлённо: язык Simula в 1960-х моделировал корабли в порту и очереди на обслуживание, и там оказалось удобно, чтобы «корабль» был одной переменной, которая сама умеет причаливать и разгружаться. Ни философии, ни «моделирования реальности» — просто способ не потерять, какие данные к чему относятся.
</Hint>

## Класс — чертёж, экземпляр — изделие

Студентов много, а описание у всех одинаковое: у каждого есть имя, группа и умение представиться. Писать это описание для каждого отдельно бессмысленно — его пишут **один раз**, а потом по нему штампуют сколько угодно студентов.

Описание называется **классом**. Конкретный студент, сделанный по описанию, — **экземпляром** (по-английски instance) или просто объектом.

Аналогия, которая держится лучше всех: класс — это чертёж детали, экземпляр — деталь, выточенная по чертежу. Чертёж нельзя взять в руки, у него нет веса и царапин; вес и царапины есть у детали. И деталей по одному чертежу можно сделать тысячу, у каждой будет свой серийный номер.

<Figure scheme="oop-class-vs-instance" caption="Класс описывает, какие поля и методы будут у объекта. Экземпляр — конкретный объект с конкретными значениями полей. Чертёж один, изделий сколько угодно." />

Вот тот же студент как класс — сразу на обоих языках.

```kotlin
// Kotlin
class Student(val name: String, val group: String) {
    fun greet(): String = "Привет, $name из группы $group"
}

val anya = Student("Аня", "ИС-31")
val marat = Student("Марат", "ИС-31")

println(anya.greet())   // Привет, Аня из группы ИС-31
println(marat.greet())  // Привет, Марат из группы ИС-31
```

```ts
// TypeScript
class Student {
  constructor(
    public readonly name: string,
    public readonly group: string,
  ) {}

  greet(): string {
    return `Привет, ${this.name} из группы ${this.group}`;
  }
}

const anya = new Student("Аня", "ИС-31");
const marat = new Student("Марат", "ИС-31");

console.log(anya.greet());
console.log(marat.greet());
```

Что совпало:

- Слово `class` и имя с большой буквы — в обоих языках одинаково.
- Скобки после имени класса — список того, что нужно для создания объекта.
- Точка — доступ к члену объекта, ровно как разобрано в главе [«Из чего состоит код»](/docs/foundation/code-basics): `anya.greet()` читается как «у объекта `anya` вызвать `greet`».
- Оба объекта сделаны по одному классу и оба помнят **свои** значения.

Что отличается:

- **Создание объекта.** В TypeScript обязательно слово `new`, в Kotlin его нет: класс вызывается как функция — `Student("Аня", "ИС-31")`.
- **Где объявлены поля.** В Kotlin `val name: String` прямо в скобках заголовка класса — это одновременно и параметр конструктора, и поле. В TypeScript то же самое достигается словом `public` (или `private`/`readonly`) перед параметром конструктора; без него параметр остался бы просто параметром и полем не стал.
- **Обращение к собственному полю.** В TypeScript обязательно `this.name`. В Kotlin внутри класса достаточно `name`, слово `this` подразумевается.

<Hint id="oop-basics-h2" type="tip">
Проверка «класс это или объект» на одну секунду: у класса нет значений. Если можно спросить «а какое там имя?» и получить ответ — перед тобой экземпляр. Если ответ «ну, там будет какое-то имя типа String» — перед тобой класс.
</Hint>

## Поля, методы и слово this

Внутри объекта живут две разные вещи, и путать их нельзя.

**Поле** (свойство, property) — переменная, принадлежащая объекту. `name`, `group`, `balance`. У каждого экземпляра свои значения полей: изменение имени у Ани никак не трогает Марата.

**Метод** — функция, принадлежащая объекту. `greet()`, `deposit()`. Метод один на весь класс: код `greet` в памяти существует в единственном экземпляре, а объектов может быть тысяча. Разница в том, что при вызове метод знает, **у какого объекта** его позвали.

Вот эта последняя мысль и есть `this`. Слово `this` внутри метода означает «тот объект, у которого метод сейчас вызвали». В `anya.greet()` внутри метода `this` — это Аня; в `marat.greet()` — Марат. Код один, `this` разный.

```kotlin
// Kotlin: this можно опустить, пока нет путаницы имён
class Counter(var value: Int) {
    fun increase(value: Int) {
        this.value = this.value + value   // this.value — поле, value — аргумент
    }

    fun show(): String = "сейчас $value"  // this не нужен, неоднозначности нет
}
```

```ts
// TypeScript: this обязателен всегда
class Counter {
  constructor(public value: number) {}

  increase(value: number): void {
    this.value = this.value + value;      // this.value — поле, value — аргумент
  }

  show(): string {
    return `сейчас ${this.value}`;        // без this.value не скомпилируется
  }
}
```

Что совпало: смысл `this` буквально один и тот же, и в обоих языках он спасает от совпадения имён поля и аргумента.

Что отличается: в Kotlin `this` пишут только там, где без него неоднозначно; в TypeScript обращение к полю **всегда** через `this.`. Забытый `this.` в TypeScript — ошибка номер один у новичков: компилятор скажет, что имя не найдено, а если такая переменная случайно есть снаружи — молча возьмёт её.

<Hint id="oop-basics-h3" type="important">
В JavaScript и TypeScript у `this` есть неприятная особенность, которой нет в Kotlin: значение `this` определяется тем, **как вызвали** функцию, а не тем, где её написали. Если передать метод куда-то как значение — например, `setTimeout(counter.show, 100)` — внутри `this` окажется не тем объектом, а `undefined`. Лечится стрелочной функцией: `setTimeout(() => counter.show(), 100)`. Пока просто запомни симптом: «объект вроде тот, а поля пустые» в JS почти всегда означает потерянный `this`.
</Hint>

## Конструктор: как объект появляется на свет

**Конструктор** — код, который выполняется в момент создания объекта. Его задача одна: привести объект в состояние, в котором им можно пользоваться. Проще говоря — заполнить поля и, если нужно, проверить, что переданные значения вообще осмысленны.

```kotlin
// Kotlin: короткая форма — параметры прямо в заголовке
class Wallet(val owner: String, var balance: Int) {
    init {
        require(balance >= 0) { "баланс не может быть отрицательным" }
    }
}

val w = Wallet("Аня", 1000)
```

```ts
// TypeScript: параметры конструктора со словом public сразу становятся полями
class Wallet {
  constructor(
    public readonly owner: string,
    public balance: number,
  ) {
    if (balance < 0) {
      throw new Error("баланс не может быть отрицательным");
    }
  }
}

const w = new Wallet("Аня", 1000);
```

Что совпало: смысл. Оба конструктора заполняют два поля и обоих не устраивает отрицательный баланс — объект с невозможным состоянием просто не создастся.

Что отличается:

- В Kotlin основной конструктор — это скобки в заголовке класса, а дополнительный код при создании кладут в блок `init`.
- В TypeScript конструктор — метод с именем `constructor`, и тело у него общее: и присваивания, и проверки.
- В Kotlin `require` бросает исключение с сообщением, в TypeScript тот же смысл записывают через `throw new Error`.

Отдельно стоит сказать, чего конструктор делать не должен: **тяжёлой работы**. Ходить в сеть, читать файлы, поднимать соединение с базой — плохая идея. Создание объекта выглядит в коде как безобидная строчка, и никто не ожидает, что она уйдёт в интернет на три секунды. Конструктор заполняет поля — всё остальное делают методы, которые вызывают явно.

<Hint id="oop-basics-h4" type="tip">
Хороший конструктор не даёт создать объект в невозможном состоянии: пустое имя, отрицательный баланс, дата рождения из будущего. Проверка в конструкторе стоит три строки, а ловит целый класс ошибок «откуда у нас в базе взялся заказ на минус двести рублей».
</Hint>

## Коробка только для данных: data class против объектного литерала

Часто нужен объект, у которого вообще нет поведения: просто набор полей, который передают между функциями. Профиль пользователя, ответ сервера, координаты точки. Тут языки расходятся заметнее всего.

```kotlin
// Kotlin: data class
data class Point(val x: Int, val y: Int)

val a = Point(1, 2)
val b = Point(1, 2)

println(a)          // Point(x=1, y=2) — читаемый вывод бесплатно
println(a == b)     // true — сравнение по значениям полей
val c = a.copy(y = 5)  // копия с изменённым полем
```

```ts
// TypeScript: интерфейс (описание формы) плюс обычный объект
interface Point {
  readonly x: number;
  readonly y: number;
}

const a: Point = { x: 1, y: 2 };
const b: Point = { x: 1, y: 2 };

console.log(a);        // { x: 1, y: 2 }
console.log(a === b);  // false — сравниваются ссылки, а не значения
const c: Point = { ...a, y: 5 };  // копия с изменённым полем
```

Это самое важное различие главы, и его стоит проговорить целиком:

- **`data class` в Kotlin — это класс**, для которого компилятор сам дописывает `toString()`, `equals()`, `hashCode()` и `copy()`. Поэтому два разных объекта с одинаковыми полями **равны** через `==`.
- **`interface` в TypeScript — это не класс, а только описание формы**, которое существует лишь во время проверки типов. После компиляции в JavaScript от него не остаётся ни строчки: в готовом коде лежит обычный объект `{ x: 1, y: 2 }`. Никакого автоматического `equals` нет — `===` для объектов сравнивает, один и тот же это объект в памяти или два разных.
- Копию с изменением в Kotlin делают методом `copy`, в TypeScript — оператором расширения `...` (spread), который раскладывает поля старого объекта в новый.

Второе различие — изменяемость полей.

| | Kotlin | TypeScript |
| --- | --- | --- |
| «менять нельзя» | `val name: String` | `readonly name: string` |
| «менять можно» | `var balance: Int` | `balance: number` |
| когда проверяется | при компиляции | при компиляции |
| остаётся ли в готовом коде | да, поле действительно без сеттера | нет, `readonly` полностью стирается |

Смысл `val` и `readonly` одинаковый: «после создания не присваивать». Но в Kotlin это свойство самого языка, а в TypeScript — подсказка проверяющему типы. В собранном JavaScript-файле никакого `readonly` нет, и код на чистом JavaScript спокойно запишет в такое поле что угодно. Для командной работы этого достаточно; защитой от злого умысла считать нельзя.

<Hint id="oop-basics-h5" type="fact">
Обе стороны надо понимать буквально: `data class` в Kotlin — это про **сгенерированный код**, `interface` в TypeScript — про **проверку без кода**. Отсюда практическое следствие: описание формы в TypeScript ничего не стоит по скорости и размеру, поэтому их пишут щедро; а `data class` — настоящий класс, и на него распространяются все обычные правила.
</Hint>

## Инкапсуляция: зачем прятать поле, если и так работает

Самый частый вопрос новичка: поле `balance` открыто, программа работает, зачем что-то усложнять. Ответ не про безопасность и не про красоту — про **количество мест, где поле может измениться**.

Пока поле открыто, изменить его может любая строка любого файла проекта. Значит, когда в базе появился отрицательный баланс, подозреваемых столько же, сколько строк в проекте. Закрыть поле и оставить два метода — значит сократить список подозреваемых до двух мест, куда можно поставить проверку и заглянуть глазами.

<Figure scheme="oop-encapsulation" caption="Поле закрыто, наружу торчат только методы. Изменить состояние можно единственным путём — через код, где живёт проверка." />

```kotlin
// Kotlin
class Wallet(private var balance: Int) {
    fun deposit(sum: Int) {
        require(sum > 0) { "пополнение должно быть положительным" }
        balance += sum
    }

    fun withdraw(sum: Int): Boolean {
        if (sum <= 0 || sum > balance) return false
        balance -= sum
        return true
    }

    fun balance(): Int = balance
}

val w = Wallet(1000)
w.deposit(500)
// w.balance = -900  // не скомпилируется: поле private
```

```ts
// TypeScript
class Wallet {
  private balance: number;

  constructor(balance: number) {
    this.balance = balance;
  }

  deposit(sum: number): void {
    if (sum <= 0) throw new Error("пополнение должно быть положительным");
    this.balance += sum;
  }

  withdraw(sum: number): boolean {
    if (sum <= 0 || sum > this.balance) return false;
    this.balance -= sum;
    return true;
  }

  getBalance(): number {
    return this.balance;
  }
}

const w = new Wallet(1000);
w.deposit(500);
// w.balance = -900;  // ошибка типов: свойство private
```

Что совпало: слово `private` пишется одинаково и означает одно и то же — «снаружи класса не видно».

Что отличается — и это важно:

- В Kotlin `private` — настоящее ограничение, оно остаётся в скомпилированном байт-коде.
- В TypeScript `private` проверяется **только компилятором**. В собранном JavaScript поле обычное, и код на JS до него дойдёт. Для настоящего сокрытия в JavaScript есть отдельный синтаксис — поле с решёткой в начале имени, `#balance`, которое недоступно снаружи по-настоящему, на уровне движка.

Уровни доступа, которые встречаются чаще всего:

| Уровень | Kotlin | TypeScript | Смысл |
| --- | --- | --- | --- |
| открыто всем | `public` (по умолчанию) | `public` (по умолчанию) | часть публичного договора класса |
| только этому классу | `private` | `private` | внутренняя кухня |
| классу и наследникам | `protected` | `protected` | нужен редко, обычно при наследовании |
| в пределах модуля | `internal` | — | нет прямого аналога, роль играет экспорт из файла |

Практическое правило, которое стоит принять сразу: **по умолчанию `private`, открываем только то, что действительно нужно снаружи**. Открыть поле позже — одна строчка. Закрыть открытое поле в проекте, где на него уже сослались в тридцати местах, — рабочий день.

И честная оговорка. Инкапсуляция не защищает от злоумышленника: в Kotlin до приватного поля добирается рефлексия, в TypeScript — обычный JavaScript. Она защищает от **случайности**: от коллеги, который в спешке присвоил поле напрямую, и от тебя самого через два месяца.

## Наследование и почему им злоупотребляют

**Наследование** — способ сказать: «этот класс — то же самое, что тот, плюс кое-что своё». Наследник получает все поля и методы родителя и может добавить свои или переопределить существующие.

```kotlin
// Kotlin: класс закрыт для наследования, пока не написано open
open class User(val name: String) {
    open fun describe(): String = "пользователь $name"
}

class Admin(name: String, val level: Int) : User(name) {
    override fun describe(): String = "админ $name уровня $level"
}

val users: List<User> = listOf(User("Аня"), Admin("Марат", 2))
users.forEach { println(it.describe()) }
```

```ts
// TypeScript: наследовать можно от любого класса, ключевых слов не нужно
class User {
  constructor(public readonly name: string) {}

  describe(): string {
    return `пользователь ${this.name}`;
  }
}

class Admin extends User {
  constructor(name: string, public readonly level: number) {
    super(name);
  }

  override describe(): string {
    return `админ ${this.name} уровня ${this.level}`;
  }
}

const users: User[] = [new User("Аня"), new Admin("Марат", 2)];
users.forEach((u) => console.log(u.describe()));
```

Что совпало: сама конструкция. Наследник вызывает конструктор родителя (`: User(name)` и `super(name)`), переопределяет метод, а список родительского типа спокойно хранит и родителей, и наследников.

Что отличается:

- **Kotlin запрещает наследование по умолчанию.** Чтобы от класса можно было наследоваться, его помечают `open`; чтобы метод можно было переопределить — тоже `open`. Это осознанное решение авторов языка: наследование — редкая операция, и разрешать её надо явно.
- **В TypeScript всё наследуемо и всё переопределяемо по умолчанию.** Слово `override` есть, но по умолчанию оно необязательно — включается настройкой компилятора. Никакого `final` для классов в TypeScript нет.
- В Kotlin слово `override` обязательно: без него код не соберётся, и это ловит опечатки в именах методов.

### Почему наследованием злоупотребляют

Наследование выглядит как бесплатное переиспользование кода: «у меня уже есть класс, который почти делает то, что нужно, — унаследуюсь и допишу». Именно это ощущение и заводит в тупик.

Три конкретные беды:

1. **Наследник получает всё, включая ненужное.** Унаследовав `RobotDog` от `Dog`, ты получил метод `eat()`, которого у робота быть не должно. Дальше его либо переопределяют пустышкой, либо он тихо живёт и однажды вызывается.
2. **Изменение в родителе ломает наследников на расстоянии.** Правишь метод в базовом классе — падают четыре класса, о существовании которых ты не помнил. Это называется хрупким базовым классом, и в больших проектах это главный источник страха перед правками.
3. **Глубина съедает понимание.** Чтобы понять, что делает метод в классе пятого уровня, надо прочитать пять файлов и держать их в голове одновременно. Практический порог — **два уровня**; всё, что глубже, обычно означает, что связь выбрана неправильно.

<Figure scheme="oop-inheritance-tree" caption="Слева цепочка наследования, где робособака унаследовала умение есть. Справа тот же класс собран из частей: берут только нужные умения." />

Проверка, которая экономит недели, — **тест «является»**. Наследование законно только тогда, когда фраза «наследник **является** родителем» верна всегда и во всех смыслах. `Admin` является `User` — да. `Square` является `Rectangle` — школьная геометрия говорит да, а код говорит нет: у прямоугольника можно менять ширину и высоту независимо, у квадрата нельзя, и наследник ломает обещание родителя. Это классический пример, на котором обжигались очень многие.

Если фраза звучит натянуто — нужна не связь «является», а связь «имеет», и о ней речь чуть ниже.

## Интерфейс — договор без исполнения

**Интерфейс** — список того, что объект обязан уметь, без единой строчки о том, как именно. Это договор: «кто подписался — обязан предоставить метод `pay(sum)`, возвращающий признак успеха». Как он внутри устроен — дело подписавшего.

<Figure scheme="oop-interface-contract" caption="Код оплаты знает только договор. Реализаций может быть сколько угодно — карта, криптокошелёк, заглушка для тестов, — и вызывающий код не меняется ни на строку." />

```kotlin
// Kotlin
interface Payment {
    fun pay(sum: Int): Boolean
}

class CardPayment(private val cardNumber: String) : Payment {
    override fun pay(sum: Int): Boolean {
        println("списываем $sum с карты $cardNumber")
        return true
    }
}

class CryptoPayment(private val wallet: String) : Payment {
    override fun pay(sum: Int): Boolean {
        println("отправляем транзакцию на $sum в кошелёк $wallet")
        return true
    }
}

fun checkout(method: Payment, sum: Int) {
    if (method.pay(sum)) println("заказ оплачен") else println("оплата не прошла")
}
```

```ts
// TypeScript
interface Payment {
  pay(sum: number): boolean;
}

class CardPayment implements Payment {
  constructor(private readonly cardNumber: string) {}

  pay(sum: number): boolean {
    console.log(`списываем ${sum} с карты ${this.cardNumber}`);
    return true;
  }
}

class CryptoPayment implements Payment {
  constructor(private readonly wallet: string) {}

  pay(sum: number): boolean {
    console.log(`отправляем транзакцию на ${sum} в кошелёк ${this.wallet}`);
    return true;
  }
}

function checkout(method: Payment, sum: number): void {
  console.log(method.pay(sum) ? "заказ оплачен" : "оплата не прошла");
}
```

Что совпало: слово `interface`, отсутствие тел у методов и главная выгода — функция `checkout` написана один раз и работает с любым способом оплаты, включая тот, который придумают через год.

Что отличается:

- В Kotlin реализация интерфейса записывается тем же двоеточием, что и наследование: `class CardPayment : Payment`. В TypeScript для этого отдельное слово — `implements`.
- В TypeScript договор может выполняться **без всякого `implements`**: если у объекта есть метод `pay` нужной формы, он подойдёт туда, где ждут `Payment`. Это называется структурной типизацией — «крякает как утка, значит утка». В Kotlin так нельзя: связь должна быть объявлена явно.
- Kotlin разрешает интерфейсу иметь методы с телом по умолчанию (наследник может не переопределять), TypeScript — нет: интерфейс там чисто описательный.

Второе отличие стоит прочувствовать на примере. В TypeScript вот это скомпилируется:

```ts
const fakePayment: Payment = {
  pay: (sum: number) => {
    console.log(`притворяемся, что списали ${sum}`);
    return true;
  },
};

checkout(fakePayment, 1000);   // работает: форма совпала
```

Никакого класса не понадобилось — обычный объектный литерал подошёл под интерфейс, потому что у него есть метод нужной формы. В Kotlin аналог пишут через анонимный объект:

```kotlin
val fakePayment = object : Payment {
    override fun pay(sum: Int): Boolean {
        println("притворяемся, что списали $sum")
        return true
    }
}

checkout(fakePayment, 1000)
```

Именно этот приём — подсунуть в качестве оплаты заглушку — делает код тестируемым: тест проверяет логику заказа, не выходя в интернет и не тратя настоящих денег.

## Полиморфизм на человеческом примере

Слово страшное, идея бытовая. **Полиморфизм** — это когда один и тот же вызов у разных объектов приводит к разному поведению, а вызывающий код об этом не знает и знать не хочет.

Человеческий пример. Учитель говорит классу: «сдайте работу». Одинаковая фраза для всех. Один сдаёт тетрадь, второй — ссылку на репозиторий, третий — файл в облаке. Учитель не проговаривает для каждого свой сценарий — он произносит одну фразу, а как именно она исполняется, решает каждый ученик. Учитель — вызывающий код, «сдать работу» — метод из договора, ученики — разные реализации.

В коде это ровно та функция `checkout` из прошлого раздела: она пишет `method.pay(sum)` и не имеет ни малейшего понятия, уйдут ли деньги на карту, в блокчейн или в тестовую заглушку.

```kotlin
// Kotlin: один цикл, три разных поведения
val methods: List<Payment> = listOf(
    CardPayment("4276 **** 1234"),
    CryptoPayment("0xA1B2"),
)

for (m in methods) checkout(m, 500)
```

```ts
// TypeScript: то же самое
const methods: Payment[] = [
  new CardPayment("4276 **** 1234"),
  new CryptoPayment("0xA1B2"),
];

for (const m of methods) checkout(m, 500);
```

Практическая ценность полиморфизма — не в красоте, а в конкретной экономии: **добавление нового варианта не требует править старый код**. Без него та же задача выглядит как длинная лестница проверок:

```kotlin
// как выглядит та же логика без полиморфизма
fun checkoutUgly(type: String, sum: Int) {
    when (type) {
        "card" -> println("списываем $sum с карты")
        "crypto" -> println("отправляем транзакцию на $sum")
        "sbp" -> println("платёж по СБП на $sum")
        else -> println("неизвестный способ оплаты")
    }
}
```

Разница в том, что произойдёт при добавлении четвёртого способа. В варианте с интерфейсом — появится новый класс, а `checkout` не изменится. В варианте с проверками — придётся найти **все** такие лестницы в проекте и дописать в каждую новую ветку; одну обязательно забудут, и она молча уйдёт в `else`.

<Hint id="oop-basics-h6" type="important">
Обратная сторона честности: лестница из проверок не всегда хуже. Если вариантов ровно три и новых не предвидится, `when` в одном месте читается лучше, чем три класса, разъехавшиеся по трём файлам. Полиморфизм окупается, когда вариантов много **и** они добавляются со временем. Один `when` на весь проект — не проблема; тот же `when`, повторённый в семи местах, — проблема.
</Hint>

## Композиция против наследования

Итог предыдущих разделов складывается в одно практическое правило, которое в индустрии повторяют десятилетиями: **предпочитай композицию наследованию**.

Разница между ними — в одном слове:

- **Наследование** — связь «является»: `Admin` **является** `User`.
- **Композиция** — связь «имеет»: `Order` **имеет** способ оплаты, `RobotDog` **имеет** умение лаять.

При композиции объект не превращается в другой объект, а держит его внутри как обычное поле и обращается к нему по имени.

```kotlin
// Kotlin: заказ имеет способ оплаты и способ доставки
class Order(
    private val payment: Payment,
    private val items: List<String>,
) {
    fun submit(sum: Int) {
        if (payment.pay(sum)) {
            println("заказ из ${items.size} позиций оформлен")
        }
    }
}

val order = Order(CardPayment("4276 **** 1234"), listOf("клавиатура", "мышь"))
order.submit(4500)
```

```ts
// TypeScript: то же самое
class Order {
  constructor(
    private readonly payment: Payment,
    private readonly items: string[],
  ) {}

  submit(sum: number): void {
    if (this.payment.pay(sum)) {
      console.log(`заказ из ${this.items.length} позиций оформлен`);
    }
  }
}

const order = new Order(new CardPayment("4276 **** 1234"), ["клавиатура", "мышь"]);
order.submit(4500);
```

Здесь `Order` ничем не наследуется. Он **держит** объект, реализующий `Payment`, и при этом:

- не получает ни одного лишнего метода;
- не ломается, когда в `CardPayment` меняют внутренности, — важен только договор `pay`;
- в тесте получает заглушку вместо настоящей оплаты, и это одна строка, а не переписывание класса;
- может поменять способ оплаты **во время работы программы**, чего наследование не умеет в принципе: класс объекта после создания не меняется.

Последний пункт часто и оказывается решающим. Наследование выбирают один раз при написании кода, композицию — каждый раз при создании объекта.

Практическая последовательность выбора, когда хочется переиспользовать чужой код:

1. Спроси: «новый класс **является** старым во всех смыслах?» Если нет — наследование сразу отпадает.
2. Если да — спроси: «нужны ли мне все методы родителя?» Если нет — снова композиция.
3. Если и тут да — проверь глубину. Третий уровень наследования почти всегда сигнал, что где-то выше связь была выбрана неверно.
4. Во всех остальных случаях — поле с объектом внутри и интерфейс между ними.

<Hint id="oop-basics-h7" type="tip">
Ключевой признак, по которому опытный человек мгновенно узнаёт лишнее наследование: наследник **переопределяет метод пустышкой** — оставляет тело пустым или бросает исключение «этот метод здесь не поддерживается». Это прямая улика: класс получил то, чего у него быть не должно, а значит, «является» тут не работает и связь надо переделать в «имеет».
</Hint>

## Один-единственный объект: object против модуля

Иногда нужен ровно один экземпляр на всю программу: конфигурация, логгер, справочник констант. Тут два языка расходятся сильнее всего, и это хороший финальный пример «идея одна, запись разная».

```kotlin
// Kotlin: object — объявление и создание одновременно
object AppConfig {
    const val API_URL = "https://api.example.com"
    var debug = false

    fun describe(): String = "$API_URL, debug=$debug"
}

println(AppConfig.API_URL)
AppConfig.debug = true
```

```ts
// TypeScript: отдельного слова не нужно — модуль сам по себе единственный
export const API_URL = "https://api.example.com";
export let debug = false;

export function describe(): string {
  return `${API_URL}, debug=${debug}`;
}

// в другом файле:
// import { API_URL, describe } from "./config";
```

Что совпало: результат. В обоих случаях получается ровно одна порция данных на всю программу, доступная по имени из любого места.

Что отличается:

- В Kotlin `object` — это **класс и его единственный экземпляр в одном объявлении**. Создать второй нельзя физически, `new` для него не существует.
- В TypeScript роль синглтона играет сам **модуль** — файл. Файл выполняется один раз при первом импорте, а дальше все, кто его импортирует, получают одни и те же значения. Отдельного ключевого слова для этого нет и не нужно.
- В Kotlin `object` внутри класса с пометкой `companion object` заменяет статические члены из Java — «функции класса, а не экземпляра». В TypeScript ту же роль играет слово `static` внутри класса или обычная экспортируемая функция.

И честное предупреждение, которое относится к обоим языкам: единственный глобальный объект с изменяемым состоянием — это **глобальная переменная**, как её ни назови. Менять `AppConfig.debug` из десяти мест так же больно, как менять любую другую глобальную переменную: неизвестно, кто менял и в каком порядке. Для неизменяемых констант — прекрасно; для состояния, которое живёт и меняется, — лучше обычный объект, который передают явно.

## Честно: где ООП помогает, а где мешает

Раздел, которого обычно нет в учебниках, потому что учебники продают подход. ООП — инструмент, а у инструмента есть область применения и есть места, где им пользоваться глупо.

### Где ООП правда помогает

- **Много однотипных сущностей со своим состоянием.** Студенты, заказы, игроки, кнопки на экране. Каждый со своими данными, у всех одинаковые операции — это ровно та задача, под которую ООП и придумали.
- **Много вариантов одного поведения.** Способы оплаты, форматы экспорта, источники данных. Интерфейс плюс несколько реализаций тут короче и надёжнее лестницы проверок.
- **Нужно подменять части при тестировании.** Заглушка вместо базы, заглушка вместо сети. Без интерфейсов это выливается в костыли и глобальные флаги.
- **Работа в команде над большим кодом.** Границы классов — это места, о которых можно договориться и дальше не мешать друг другу.
- **Готовые библиотеки и фреймворки.** В Android половина работы — это переопределение методов классов Android SDK. Даже если ты сам не сторонник ООП, читать этот код придётся.

### Где ООП мешает

- **Маленький скрипт.** Программа на пятьдесят строк, которая читает файл и печатает статистику, не нуждается ни в одном классе. `class DataProcessor` с единственным методом `process()` — это функция, вокруг которой зачем-то построили стену.
- **Класс без состояния.** Если у класса нет полей, а есть только методы, — это набор функций, и честнее оставить его набором функций. В Kotlin для этого есть функции верхнего уровня, в TypeScript — экспортируемые функции модуля.
- **Преждевременная иерархия.** Пять интерфейсов и три уровня наследования, написанные «на вырост», под будущие требования, которых ещё нет. В девяти случаях из десяти будущее приходит другим и всю иерархию приходится ломать.
- **Обработка данных.** Разбор CSV, фильтрация, подсчёт сумм: здесь выигрывают функции и цепочки преобразований (`map`, `filter`, `sum`), а не объекты. Оба наших языка это прекрасно умеют.
- **Размазанное состояние.** Когда объектов много и каждый меняет свои поля, ответ на вопрос «в каком состоянии сейчас программа» собирается по кусочкам из всех объектов. Это реальная цена ООП, и именно из-за неё в современном коде так любят неизменяемые данные — `val` и `readonly` вместо `var`.

### Три признака, что ООП применили не туда

1. **Класс, у которого один метод и никаких полей.** Это функция.
2. **Классы `Manager`, `Processor`, `Helper`, `Handler`.** Имена без содержания почти всегда означают, что класс создан ради класса, а не ради конкретной ответственности.
3. **Чтобы понять одну строчку, нужно открыть пять файлов.** Абстракций стало больше, чем задачи.

Здоровое отношение звучит так: **классы появляются тогда, когда без них становится хуже, а не заранее**. Начинать с функций — нормально. Заметил, что четыре функции подряд принимают одни и те же три аргумента, — вот в этот момент и родился класс, естественно и по делу.

| --- | --- | --- |
| объявить класс | `class Student(val name: String)` | `class Student { constructor(public name: string) {} }` |
| создать объект | `Student("Аня")` | `new Student("Аня")` |

<details>
<summary>Углубиться</summary>

**Абстрактный класс — гибрид класса и интерфейса.** Класс, который нельзя создать напрямую: часть методов у него с телом, часть — только объявлена, и наследник обязан их дописать. В Kotlin это `abstract class`, в TypeScript — тоже `abstract class`. Берут его, когда у реализаций правда есть общий код; если общего кода нет — хватает интерфейса.

**Структурная и номинальная типизация.** Это то самое различие с `implements`. TypeScript смотрит на форму объекта: подходит форма — подходит объект. Kotlin смотрит на объявленное имя типа. Из-за этого в TypeScript легче писать тесты и легче случайно передать не то: два разных по смыслу типа с одинаковыми полями там взаимозаменяемы.

**SOLID.** Набор из пяти принципов проектирования классов, о которых спрашивают на собеседованиях. Один из них — принцип подстановки Барбары Лисков — это формальная версия теста «является» из этой главы, а история с квадратом и прямоугольником — его каноническая иллюстрация. Читать SOLID имеет смысл после того, как своими руками написан код, где иерархия сломалась: до этого он выглядит набором лозунгов.

**Делегирование в Kotlin.** У Kotlin есть слово `by`, которое делает композицию такой же короткой, как наследование: класс реализует интерфейс, а всю работу автоматически перекладывает на объект в поле. Это буквально языковая поддержка правила «композиция вместо наследования».

**Модификатор `sealed`.** Kotlin умеет запечатывать иерархию: список наследников фиксирован и известен компилятору, поэтому в `when` он проверит, что разобраны все варианты. Часто это лучше и наследования, и лестницы проверок. В TypeScript похожего эффекта добиваются размеченными объединениями типов.

## Куда дальше: проверенные ресурсы

<Block kind="cheatsheet" title="ООП: официальные источники по обоим языкам" chapterId="oop-basics" blockId="cheatsheet-resources">

- [Kotlin: Classes](https://kotlinlang.org/docs/classes.html) — первоисточник про классы, конструкторы и блок `init`.
- [Kotlin: Inheritance](https://kotlinlang.org/docs/inheritance.html) — `open`, `override`, вызов конструктора родителя.
- [Kotlin: Interfaces](https://kotlinlang.org/docs/interfaces.html) — договоры, методы с реализацией по умолчанию, анонимные объекты.
- [Kotlin: Data classes](https://kotlinlang.org/docs/data-classes.html) — что именно генерирует компилятор: `equals`, `toString`, `copy`.
- [Kotlin: Visibility modifiers](https://kotlinlang.org/docs/visibility-modifiers.html) — `private`, `protected`, `internal` и их область действия.
- [Kotlin: Object declarations](https://kotlinlang.org/docs/object-declarations.html) — `object`, `companion object` и анонимные объекты.
- [Kotlin: Delegation](https://kotlinlang.org/docs/delegation.html) — слово `by`: композиция без ручного проброса методов.
- [TypeScript Handbook: Classes](https://www.typescriptlang.org/docs/handbook/2/classes.html) — параметры-свойства, `readonly`, `private`, `implements`, `override`.
- [TypeScript Handbook: Object Types](https://www.typescriptlang.org/docs/handbook/2/objects.html) — интерфейсы, необязательные поля, расширение типов.
- [MDN: Classes в JavaScript](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Classes) — что происходит с классом после компиляции TypeScript, включая приватные поля с решёткой.
- [MDN: this](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/this) — подробный разбор, почему `this` в JavaScript зависит от способа вызова.
- [MDN: наследование и цепочка прототипов](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Inheritance_and_the_prototype_chain) — как наследование устроено под капотом в JavaScript.
