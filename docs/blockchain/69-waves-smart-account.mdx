# Смарт-аккаунт: скрипт вместо одной подписи

## Зачем это нужно

Обычный аккаунт работает по одному правилу: «подпись верна — пропускаем». В предыдущей главе мы написали это правило на RIDE и увидели, что оно стоит 182 единицы сложности.

А теперь главное: это правило можно **заменить**. Навесить на обычный аккаунт скрипт — и он начнёт пропускать транзакции по своему собственному условию. Две подписи из трёх. Никаких переводов до определённой даты. Только записи данных, но не деньги. Что угодно, что выражается в RIDE.

Такой аккаунт называется **смарт-аккаунтом**, и это самая недооценённая возможность Waves: в Ethereum ровно то же самое требует отдельного контракта-кошелька и куда больше кода.

Эта глава — про то, как это делается, сколько стоит и где подводные камни. Все ответы узла сняты на локальном узле Waves 1.6.4.

## Скрипт-турникет

<Figure scheme="wsa-turnstile" caption="Скрипт решает про исходящие транзакции: true пропускает, false отказывает" />

Начнём с очевидного правила — «переводы запрещены»:

```ride
{-# STDLIB_VERSION 6 #-}
{-# CONTENT_TYPE EXPRESSION #-}
{-# SCRIPT_TYPE ACCOUNT #-}
match tx {
  case t: TransferTransaction => false
  case _ => sigVerify(tx.bodyBytes, tx.proofs[0], tx.senderPublicKey)
}
```

```text
сложность: 183
```

Ставим:

```js
const { setScript } = require('@waves/waves-transactions');
const ss = setScript({ script: compiled.base64, chainId: 'R' }, seed);
```

```text
в блоке: 30
```

Проверим, что было до и что стало после. **До установки** тот же перевод проходил:

```text
ответ: 200
```

**После:**

```text
код: 400
{"error":307,"message":"Transaction is not allowed by account-script"}
```

<SyntaxBreakdown parts={[
  { text: 'error: 307', label: 'код отказа скрипта', note: 'отличается от 112: там проверка состояния, здесь именно скрипт сказал «нет»' },
  { text: 'not allowed by account-script', label: 'формулировка', note: 'одна на все случаи: скрипт не объясняет, что именно ему не понравилось' },
]} />

А запись данных по-прежнему проходит — её пропускает ветка `case _`:

```text
код: 200 | в блоке: 30
```

<Hint type="important">
Скрипт решает только про **исходящие** транзакции. Входящий перевод он остановить не может: транзакция подписана отправителем, а не вами, и ваш скрипт в ней не участвует. Задача «не принимать деньги» на смарт-аккаунте не решается — её решают смарт-активом.
</Hint>

## Что видит скрипт

Внутри скрипта доступно одно значение — `tx`, сама транзакция. Что в нём есть, зависит от типа, поэтому почти каждый скрипт начинается с `match`.

| Поле | Что в нём |
| --- | --- |
| `tx.bodyBytes` | тело транзакции в байтах — то, что подписано |
| `tx.proofs` | массив подписей, до восьми мест |
| `tx.senderPublicKey` | публичный ключ отправителя |
| `tx.fee` | комиссия |
| `t.amount`, `t.recipient` | у перевода — сумма и получатель |
| `d.data` | у транзакции данных — список записей |

<Hint type="tip">
`sigVerify(tx.bodyBytes, tx.proofs[0], tx.senderPublicKey)` — это ровно поведение обычного аккаунта, записанное вручную. Полезно держать эту строку в голове как «ничего не изменилось»: любой скрипт-проверяющий отличается от неё только добавленными условиями.
</Hint>

## Две подписи из трёх

Вот ради чего всё затевалось. Счёт, которым распоряжаются трое, и любые двое из них могут отправить транзакцию:

```ride
{-# STDLIB_VERSION 6 #-}
{-# CONTENT_TYPE EXPRESSION #-}
{-# SCRIPT_TYPE ACCOUNT #-}

let alice = base58'FmEEYNK6ZxyC…'
let boris = base58'8cbuFR33cJ9x…'
let sonya = base58'6ZwCUSYEc5CA…'

let a = if sigVerify(tx.bodyBytes, tx.proofs[0], alice) then 1 else 0
let b = if sigVerify(tx.bodyBytes, tx.proofs[1], boris) then 1 else 0
let s = if sigVerify(tx.bodyBytes, tx.proofs[2], sonya) then 1 else 0

a + b + s >= 2
```

```text
сложность: 549
```

<SyntaxBreakdown parts={[
  { text: "base58'FmEEYNK6ZxyC…'", label: 'публичный ключ прямо в коде', note: 'запись base58\'…\' превращает строку в байты на этапе компиляции' },
  { text: 'tx.proofs[0]', label: 'место закреплено', note: 'нулевое место — за Алисой; подпись Бориса там не засчитается' },
  { text: 'if … then 1 else 0', label: 'счёт подписей', note: 'булево значение в число превращают вручную: приведения типов в языке нет' },
  { text: 'a + b + s >= 2', label: 'условие', note: 'последнее выражение и есть ответ скрипта' },
]} />

<Figure scheme="wsa-proofs" caption="Каждое место в массиве закреплено за своим ключом" />

**Одна подпись из трёх:**

```text
код: 400 | Transaction is not allowed by account-script
```

**Две подписи:**

```text
код: 200 | принято | в блоке: 149
```

**Две подписи, но в перепутанных местах** — подпись Бориса положили в нулевое место, Алисы в первое:

```text
код: 400 | Transaction is not allowed by account-script
```

<Hint type="important">
Порядок в `proofs` — не формальность. Скрипт проверяет конкретное место конкретным ключом. Если подписант не участвует, на его место кладут **пустую строку** — это законное значение, означающее «этот не подписывал».
</Hint>

## Доплата за сложность

При первой же попытке отправить транзакцию с такого счёта узел сказал неожиданное:

```text
State check failed. Reason: Transaction sent from smart account. Requires 400000 extra fee.
Fee for TransferTransaction (100000 in WAVES) does not exceed minimal value of 500000 WAVES.
```

<Figure scheme="wsa-extra-fee" caption="Граница — сложность 200: до неё смарт-аккаунт платит как обычный" />

Правило такое: если сложность проверяющего **больше 200**, к комиссии каждой исходящей транзакции добавляется 0,004 WAVES. Проверяется это одним запросом:

```bash
curl .../addresses/scriptInfo/<адрес>
```

```text
сложность проверяющего: 183 | доплата: 0
сложность проверяющего: 549 | доплата: 400000
```

Первый скрипт — «переводы запрещены», сложность 183, доплаты нет. Второй — две подписи из трёх, сложность 549, доплата есть.

<Hint type="fact">
Отсюда практический приём: если проверяющий слегка не укладывается в 200, его стоит подсократить — уложиться выгоднее, чем платить впятеро за каждую транзакцию. Например, `valueOrElse` стоит дороже, чем `getIntegerValue`, а лишний `sigVerify` — 182 единицы сам по себе.
</Hint>

## Снять скрипт

Скрипт можно убрать — если он сам это разрешает:

```js
const off = setScript({ script: null, chainId: 'R' }, seed);
```

```text
код: 200
скрипт после снятия: {"script":null,"complexity":0,"extraFee":0,"publicKey":null}
```

Аккаунт снова стал обычным.

<Hint type="important">
Скрипт может **запретить сам себя снимать** — достаточно ветки `case s: SetScriptTransaction => false`. Такой аккаунт останется со своим правилом навсегда. Это мощный приём и одновременно способ заблокировать счёт насмерть: проверяйте, что при отладке такая ветка не попала в код случайно.
</Hint>

## Типичные ошибки

**Ошибка 1. Забыть про доплату.**

```text
Transaction sent from smart account. Requires 400000 extra fee.
```

Библиотека считает комиссию по типу транзакции и про скрипт на счёте не знает. Ставить надо вручную.

**Ошибка 2. Сдвигать подписи вместо пустых мест.**

Подписант не участвует — на его месте пустая строка, а не отсутствие элемента. Сдвиг ломает соответствие.

**Ошибка 3. Запретить всё, включая снятие скрипта.**

```ride
match tx {
  case _ => false      // счёт заблокирован навсегда
}
```

Потерять так учебный счёт не страшно, рабочий — очень.

**Ошибка 4. Ожидать, что скрипт остановит входящие.**

Не остановит. Скрипт — про исходящие.

**Ошибка 5. Думать, что отказ объяснится.**

`Transaction is not allowed by account-script` — это всё, что будет сказано. Какое именно условие не сошлось, узел не сообщает: отлаживать приходится, упрощая скрипт по частям.

## Что должен уметь после главы

- поставить скрипт на аккаунт и снять его;
- объяснить, что скрипт решает только про исходящие транзакции;
- написать проверяющего, запрещающего определённый вид транзакций;
- собрать счёт с двумя подписями из трёх и объяснить роль мест в `proofs`;
- посчитать доплату по сложности и узнать её через `scriptInfo`;
- назвать способ заблокировать счёт навсегда — и не сделать этого случайно.
