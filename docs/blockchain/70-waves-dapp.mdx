## Зачем это нужно

Смарт-аккаунт из прошлой главы умеет только одно: сказать «да» или «нет» на свою же исходящую транзакцию. Этого хватает для многоподписного счёта, но не хватает для приложения.

Чтобы появилось приложение, скрипт должен уметь две вещи: **принимать вызовы снаружи** и **менять состояние**. Именно это и добавляет второй вид скрипта — `DAPP`.

Мы напишем на нём ту же зачётку, что уже писали на Solidity и чейнкодом Fabric. Сравнение получится честным: одна задача, третья платформа. Всё ниже — прогон на локальном узле Waves 1.6.4.

## Устройство вызываемой функции

```ride
{-# STDLIB_VERSION 6 #-}
{-# CONTENT_TYPE DAPP #-}
{-# SCRIPT_TYPE ACCOUNT #-}

@Callable(i)
func zavesti(id: String, fio: String) = {
  let kluch = "z_" + id
  match getString(this, kluch) {
    case s: String => throw("Zachetka " + id + " uzhe zavedena")
    case _ => [ StringEntry(kluch, fio), IntegerEntry(kluch + "_ball", 0) ]
  }
}
```

## Что можно положить в список

<Figure scheme="wdp-actions" caption="Всё, что делает dApp, — в этом списке; другого способа менять мир у него нет" />

| Действие | Что делает |
| --- | --- |
| `IntegerEntry`, `StringEntry` | записать число или строку в своё состояние |
| `BooleanEntry`, `BinaryEntry` | записать да-нет или байты |
| `DeleteEntry` | удалить ключ |
| `ScriptTransfer` | отправить деньги со счёта dApp |
| `Issue`, `Reissue`, `Burn` | выпустить, допечатать, сжечь токен |
| `Lease`, `LeaseCancel`, `SponsorFee` | аренда и спонсирование комиссий |

<Hint type="important">
Функция ничего не делает сама — она **возвращает список**. Пока функция считает, ничего не записано; если где-то по дороге сработает `throw`, не запишется вообще ничего. Это и есть встроенная «всё или ничего», которую в Solidity обеспечивает `revert`.
</Hint>

## Кто вызывает и чьё состояние меняется

<Figure scheme="wdp-who" caption="i.caller — вызвавший, this — сам dApp; перепутать их значит написать не ту программу" />

Внутри функции доступны два разных адреса, и путать их нельзя:

- **`this`** — аккаунт, на котором стоит скрипт. Записи идут в **его** состояние, деньги `ScriptTransfer` уходят с **его** счёта.
- **`i.caller`** — тот, кто вызвал функцию. Он подписал транзакцию типа 16 и заплатил комиссию.

Отсюда типичный приём — привязать данные к вызвавшему составным ключом:

```ride
func kluch(a: Address) = "vklad_" + a.toString()
```

<Hint type="important">
Состояние вызвавшего dApp изменить **не может**. Он пишет только в своё. Поэтому все данные пользователей хранятся в состоянии самого приложения, и ключи делают составными — иначе двум пользователям не разойтись.
</Hint>

Вместе с `i` приезжает ещё несколько полезных вещей:

| Поле | Что в нём |
| --- | --- |
| `i.caller` | адрес вызвавшего |
| `i.callerPublicKey` | его публичный ключ |
| `i.payments` | что приложено к вызову (следующая глава) |
| `i.transactionId` | идентификатор этой транзакции |
| `i.fee` | заплаченная комиссия |

## Отказы

Вторая функция — с проверкой диапазона:

```ride
@Callable(i)
func postavit(id: String, ball: Int) = {
  let kluch = "z_" + id
  strict fio = getStringValue(this, kluch)
  if (ball < 2 || ball > 5) then throw("Ball vne diapazona 2..5")
  else [ IntegerEntry(kluch + "_ball", ball) ]
}
```

Обратите внимание на `strict`: чтение нужно ради **побочного эффекта** — упасть, если зачётки нет. Под `let` эта проверка бы не выполнилась.

Три отказа подряд, все с живого узла:

```text
повторное заведение:
{"error":306,"message":"Error while executing dApp: Zachetka z-1 uzhe zavedena"}

балл вне диапазона:
{"error":306,"message":"Error while executing dApp: Ball vne diapazona 2..5"}

несуществующая функция:
{"error":306,"message":"Error while executing dApp: @Callable function 'netTakoy' doesn't exist in the script"}
```

<Hint type="fact">
`error: 306` — «скрипт dApp упал». В отличие от смарт-аккаунта, здесь узел передаёт **ваш текст** из `throw`. Поэтому сообщения стоит писать осмысленно: они и есть интерфейс ошибок вашего приложения.
</Hint>

## Та же задача на трёх платформах

Стоит сравнить прямо сейчас, пока все три реализации свежи.

| | Solidity | Чейнкод Fabric | dApp на RIDE |
| --- | --- | --- | --- |
| Где данные | поля контракта | общее хранилище | состояние аккаунта |
| Проверка | `require` | `throw` | `throw` |
| Возврат результата | изменяет поля | `putState` | список действий |
| «Всё или ничего» | `revert` | набор изменений | список не вернулся |
| Кто вызвал | `msg.sender` | `ctx.clientIdentity` | `i.caller` |
| Стоимость вызова | ~96 000 газа | нет платы | 0,005 WAVES |

Логика во всех трёх одинаковая, а вот способ вернуть результат — разный. В RIDE он самый непривычный и самый строгий: функция **описывает** изменения, а применяет их сеть.

## Типичные ошибки

**Ошибка 1. Вернуть действие вместо списка.**

```text
CallableFunction needs to return (List[BinaryEntry|BooleanEntry|…], Any) | List[…]
```

Даже одно действие оборачивают в квадратные скобки.

**Ошибка 2. Проверка под `let`.**

Та же ловушка, что и в прошлой главе, но здесь дороже: проверка в dApp защищает чужие деньги.

**Ошибка 3. Писать в состояние вызвавшего.**

Нельзя. Данные пользователей живут в состоянии dApp под составными ключами.

**Ошибка 4. Две функции с одинаковым именем.**

```text
Compilation failed: [Value 'f' can't be defined because function with this name is already defined]
```

Перегрузки функций в RIDE нет.

**Ошибка 5. Не проверить `applicationStatus`.**

Вызов может попасть в блок и не примениться. Проверять надо не код ответа, а состояние или `stateChanges`.

- написать dApp с вызываемыми функциями и установить его на аккаунт;
