## Зачем это нужно

Подключённый кошелёк нужен шапке, форме вклада и списку операций. Список операций нужен и списку, и счётчику в шапке. Признак «идёт транзакция» — кнопке, полоске состояния и блокировке формы.

Пока значений три и экран один, всё решается подъёмом состояния к общему родителю. Как только экранов становится пять, общий родитель оказывается корнем приложения — и значения приходится передавать через все уровни вниз.

Эта глава — про то, во что это обходится, и про другой способ: **одно хранилище, из которого каждый берёт то, что ему нужно**.

## Цена протаскивания через уровни

Прогон строит два одинаковых дерева из семи компонентов. В первом значение идёт свойствами сверху вниз, во втором его берут из хранилища прямо там, где оно нужно. Меняем значение и считаем, сколько функций вызвалось заново:

```text
── значение идёт свойствами через пять уровней ──
  App: 1, Sidebar: 1, L1: 1, L2: 1, L3: 1, L4: 1, L5: 1
  всего вызовов: 7      на экране: 2.5

── значение берут из хранилища там, где оно нужно ──
  L5: 1
  всего вызовов: 1      на экране: 2.5
```

<Figure scheme="wrx-prop-drilling" caption="Семь вызовов против одного; на экране при этом одно и то же" />

Обратите внимание на **`Sidebar`**: меню не имеет к сумме никакого отношения, но пересчиталось вместе со всеми, потому что его родитель пересчитался.

Дело не столько в скорости — семь вызовов ничего не стоят. Дело в том, что промежуточные компоненты **вынуждены знать** про значение, которое им не нужно: принимать его, объявлять в типах и передавать дальше. Через полгода никто не может убрать свойство, потому что непонятно, кому оно нужно.

<Hint type="fact">
Не всякое общее значение требует хранилища. Для «редко меняющегося и всем нужного» — темы оформления, языка, адреса контракта — в React есть встроенный способ раздать значение вглубь без передачи через уровни. Хранилище нужно там, где значение **часто меняется** и меняют его из разных мест.
</Hint>

## Идея: одно состояние, один путь его менять

Три правила, из которых состоит вся библиотека:

1. **Состояние приложения — один объект.** Не разбросано по компонентам, а лежит в одном месте.
2. **Менять его напрямую нельзя.** Можно только отправить **действие** — объект, описывающий, что произошло.
3. **Новое состояние вычисляет обычная функция** от старого состояния и действия.

<Figure scheme="wrx-store-flow" caption="Действие → обработчик → новое состояние → подписчики; другого пути внутрь нет" />

Из третьего правила следует главное свойство: **всё, что происходило в приложении, описано списком действий**. Сохранили список — можете воспроизвести состояние; показали список — видно, что делал пользователь.

<SectionAnchor chapterId="web-redux" sectionId="ideya" />

## Хранилище работает и без React

Важное, что теряется при быстром знакомстве: библиотека хранилища **не имеет отношения к React**. Прогон создаёт хранилище и работает с ним напрямую:

```text
── хранилище живёт само по себе ──
  начальное состояние: {"amount":"0","ops":[],"busy":false}

── что записалось, шаг за шагом ──
  1) {"amount":"2.5","ops":[],"busy":false}
  2) {"amount":"2.5","ops":[{"hash":"0xabc","amount":"2.5"}],"busy":false}
  3) {"amount":"2.5","ops":[{"hash":"0xabc","amount":"2.5"}],"busy":true}
```

```js
const store = configureStore({ reducer: { vault: vault.reducer } });

store.getState();                              // прочитать
store.subscribe(() => { … });                  // узнавать об изменениях
store.dispatch(vault.actions.setAmount("2.5")); // изменить
```

## Действие: объект с именем

```text
── что такое действие ──
  {"type":"vault/setAmount","payload":"7"}
  имя действия: vault/setAmount
```

Действие — **обычный объект** с обязательным полем-именем и, обычно, полезной нагрузкой. Имя складывается из названия раздела и названия действия; в списке отправленных действий такие имена читаются как рассказ о происходившем.

Имена пишут **от лица события, а не команды**: не «поставить сумму», а «пользователь ввёл сумму»; не «добавить операцию», а «транзакция подтверждена». Разница проявляется, когда на одно событие должны отреагировать два раздела: команда адресована одному, событие — всем, кому интересно.

<SectionAnchor chapterId="web-redux" sectionId="deystvie" />

## Обработчик: обычная функция

```text
── обработчик — обычная функция от состояния и действия ──
  одинаковый вход два раза → одинаковый выход: true
  результат: {"amount":"9","ops":[],"busy":false}
```

Обработчик — функция `(состояние, действие) → новое состояние`. Никакой магии: её можно вызвать руками, как в прогоне, и проверить.

Из этого следуют два практических вывода.

**Обработчики — самое простое место для тестов.** Ни сети, ни браузера, ни React: вход и выход.

**В обработчике не бывает запросов, таймеров и случайных чисел.** Он обязан быть вычислением — по тем же причинам, по которым им обязан быть компонент. Куда девать всё остальное — тема следующих двух глав.

## «Меняем на месте», а старое цело

В обработчике пишут так, будто состояние меняют напрямую:

```js
reducers: {
  setAmount: (s, a) => { s.amount = a.payload; },
  addOp:     (s, a) => { s.ops.push(a.payload); },
}
```

Это выглядит нарушением всех правил. Прогон проверяет, что произошло на самом деле:

```text
── старое состояние не тронуто ──
  прежний объект целиком: {"amount":"0","ops":[],"busy":false}
  это тот же объект?      : false
  массив операций тот же? : false
  (а ведь в обработчике написано ops.push — но исходный массив остался пустым)
```

<Figure scheme="wrx-immutable" caption="Запись «изменяем на месте» — обман зрения: из черновика собирается новый объект" />

Библиотека передаёт в обработчик не само состояние, а **черновик**, который записывает все обращения. По окончании из черновика собирается новый объект — старый остаётся нетронутым.

Зачем такая сложность: **сравнение по ссылке**. Раз при любом изменении получается новый объект, React достаточно сравнить ссылки, чтобы понять, изменилось что-то или нет. Это то же правило, что в главе про состояние: массив, изменённый на месте, не вызывает перерисовки.

<Hint type="important">
Черновик работает **только внутри обработчика**. Значение, полученное из хранилища в компоненте, менять нельзя ни в коем случае: это настоящее состояние, и его изменение не заметит никто — ни React, ни сама библиотека.
</Hint>

## Когда хранилище нужно, а когда нет

**Нужно:** значение меняется часто и меняется из разных мест. Подключённый кошелёк, список операций, признак идущей транзакции, выбранная сеть.

**Не нужно:** значение живёт внутри одного компонента. Открыт ли выпадающий список, что набрано в поле, какая вкладка выбрана. Класть такое в общее хранилище — значит превратить простую вещь в три файла.

**Спорно:** данные, приходящие из сети. Их состояние (загрузка, ошибка, значение) отлично ложится в хранилище, но для этого есть отдельные средства — о них в последней главе блока.

## Типичные ошибки

**Кладут в хранилище всё.** Включая открытые выпадающие списки. Проект обрастает действиями на каждое движение мыши.

**Меняют то, что пришло из хранилища, в компоненте.** Изменение не увидит никто, а отладка займёт час.

**В обработчике делают запрос.** Обработчик обязан быть вычислением.

**Хранят в состоянии вычислимое.** Сумму, которую можно посчитать по списку. Однажды они разойдутся.

**Действия называют командами.** «Установить сумму» вместо «пользователь ввёл сумму»: на одно событие реагировать двум разделам становится неудобно.

**Берут из хранилища весь объект целиком.** Компонент начинает пересчитываться на любое изменение чего угодно — и выигрыш, ради которого всё затевалось, исчезает.

**Заводят хранилище там, где хватило бы подъёма состояния.** Три компонента и одно значение — это не тот случай.

## Слова главы

<Block kind="vocab">

- **Протаскивание через уровни** — передача значения свойствами сквозь компоненты, которым оно не нужно.
- **Хранилище** — один объект состояния на всё приложение; работает и без React.
- **Действие** — объект с именем и нагрузкой; единственный способ сообщить об изменении.
- **Обработчик** — чистая функция от состояния и действия к новому состоянию.
- **Отправка действия** — синхронна: после возврата новое состояние уже на месте.
- **Подписка** — вызывается после каждого применённого действия.
- **Черновик** — то, что приходит в обработчик; из него собирается новый объект.
- **Сравнение по ссылке** — почему неизменяемость важна: новый объект виден сразу.

</Block>

## На чемпионате

**Не начинайте с хранилища.** Начните с подъёма состояния. Хранилище добавляют тогда, когда протаскивание через уровни начинает мешать, — обычно на третьем-четвёртом экране.

**Разделов немного и по смыслу.** Кошелёк, операции, форма. Не «один раздел на компонент».

**Имена действий читаемы.** На защите список отправленных действий — готовый рассказ о том, что делал пользователь.

**Обработчики покройте тестами.** Это самое дешёвое тестирование во всём фронтенде: вход, выход, ни одной подделки.

И честно: для интерфейса из четырёх экранов хранилище — не обязательное требование. Оно становится выгодным, когда состояние действительно общее. Задание его упоминает, и знать его надо; применять — по делу.

## Куда углубиться

- **Средства отладки в браузере** — список действий, состояние на каждом шаге, переход назад по истории.
- **Промежуточные обработчики** — как действие проходит через цепочку перед тем, как попасть в обработчик.
- **Встроенный способ раздать значение вглубь** — чем он отличается от хранилища и когда его достаточно.
- **Нормализация данных** — почему список операций хранят как карту по идентификатору.
- **Сохранение состояния между заходами** — и чего в него класть нельзя.
