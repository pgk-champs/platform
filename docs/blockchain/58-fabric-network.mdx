## Зачем это нужно

В прошлой главе сеть поднялась одной командой, и канал создался второй. Это удобно, пока всё работает. Как только что-то откажет — а откажет обязательно, — придётся понимать, что именно эти команды сделали.

Настройки канала не спрятаны в конфигурационном файле на диске. Они лежат **внутри самого канала**, в его первом блоке, и меняются такой же транзакцией, как любая запись. Достать их можно в любой момент и прочитать глазами.

Эта глава — про то, что там лежит: кто состоит в канале, по каким правилам принимаются решения, как из потока сделок получаются блоки и почему у Fabric нет откатов.

## Достаём настройки канала

```bash
peer channel fetch config config_block.pb -o localhost:7050 \
  --ordererTLSHostnameOverride orderer.example.com \
  -c pgk --tls --cafile "$ORDERER_CA"
```

<SyntaxBreakdown parts={[
  { text: 'channel fetch config', label: 'что скачиваем', note: 'не любой блок, а последний блок с настройками — их может быть несколько за жизнь канала' },
  { text: 'config_block.pb', label: 'куда', note: 'двоичный файл в формате protobuf; читать его напрямую бесполезно' },
  { text: '--ordererTLSHostnameOverride', label: 'имя в сертификате', note: 'стучимся на localhost, а в сертификате упорядочивателя написано orderer.example.com — этот флаг гасит несовпадение' },
  { text: '--cafile', label: 'кому доверяем', note: 'корневой сертификат упорядочивателя; без него соединение не установится' },
]} />

```text
INFO [cli.common] readBlock -> Received block: 2
```

Двоичный файл превращается в читаемый JSON отдельной утилитой:

```bash
configtxlator proto_decode --input config_block.pb --type common.Block --output config.json
```

<Hint type="tip">
`configtxlator` — «переводчик» между двоичным форматом и JSON в обе стороны. Именно через него меняют настройки канала: скачали, перевели в JSON, поправили, перевели обратно, отправили как транзакцию.
</Hint>

## Кто состоит в канале

В расшифрованных настройках интересна ветка `channel_group.groups.Application`:

```text
организации канала: Org1MSP, Org2MSP
```

Две организации. Каждая описана своим **MSP** — набором сертификатов, по которым сеть узнаёт «своих». Английское сокращение расшифровывается как «поставщик услуг членства», но по сути это ответ на вопрос: **какие подписи считать подписями этой организации**.

<Figure scheme="fn-msp-folder" caption="Папка личности: сертификат и ключ — ваши, корневые сертификаты — организации" />

Личность одного участника — четыре вещи в папке:

- `signcerts/` — сертификат: кто вы, из какой организации, какая роль;
- `keystore/` — закрытый ключ, которым подписываются запросы;
- `cacerts/` — корневой сертификат организации: кем вы заверены;
- `tlscacerts/` — корень для шифрования соединения.

Роль записана прямо в сертификате, в поле подразделения:

```text
subject=... OU=admin, CN=Admin@org1.example.com     ← человек-администратор
subject=... OU=peer,  CN=peer0.org1.example.com     ← узел
```

<Hint type="important">
Роль — не пометка для красоты. Политики ссылаются именно на неё: «подтверждать сделки может только `PEER`», «менять настройки — только `ADMIN`». Выдали человеку сертификат с ролью `peer` — он получил права узла.
</Hint>

## Политики: два уровня

Самое важное место настроек — политики. Здесь легко запутаться, потому что они двухуровневые.

<Figure scheme="fn-policy-levels" caption="Правило канала ссылается на организации, правило организации — на роли в сертификатах" />

**Уровень канала** — правила вида «сколько организаций должны согласиться»:

```text
Readers              → ANY of Readers
Writers              → ANY of Writers
Endorsement          → MAJORITY of Endorsement
LifecycleEndorsement → MAJORITY of LifecycleEndorsement
Admins               → MAJORITY of Admins
```

Читается так: «чтобы прочитать — достаточно **любой** организации; чтобы подтвердить сделку — нужно **большинство** организаций».

**Уровень организации** — правила вида «чьи подписи считаются подписью организации»:

```text
Org1MSP:
  Endorsement → Org1MSP/PEER
  Writers     → Org1MSP/ADMIN, Org1MSP/CLIENT
  Readers     → Org1MSP/ADMIN, Org1MSP/PEER, Org1MSP/CLIENT
  Admins      → Org1MSP/ADMIN
```

Сложим два уровня. Правило «подтвердить сделку» на канале — `MAJORITY of Endorsement`. Организаций две, большинство из двух — это две. Правило `Endorsement` у каждой организации — подпись её пира. Итого: **сделку должны подписать пиры обеих организаций**. Это и есть тот самый ответ, из-за которого в следующих главах будут отказы.

<Hint type="fact">
Двухуровневость — не усложнение ради усложнения. Она позволяет добавить в канал третью организацию, ничего не переписывая на верхнем уровне: правило `MAJORITY` само начнёт означать «двое из трёх».
</Hint>

## Опорный пир

В настройках каждой организации есть отдельное поле:

```text
anchor peers Org1: {"anchor_peers":[{"host":"peer0.org1.example.com","port":7051}]}
```

**Опорный пир** — тот узел организации, через который с ней знакомятся пиры других организаций. Пиры внутри канала непрерывно обмениваются сведениями о том, кто жив и у кого какая высота цепочки. Чтобы этот обмен начался между **разными** организациями, каждая должна объявить хотя бы один адрес, доступный снаружи.

Забыть объявить опорный пир — классическая ошибка. Сеть при этом работает: каждая организация живёт своей жизнью, блоки получает от упорядочивателя. Не работает ровно одно — сбор подписей с чужих пиров, потому что клиент не знает их адресов. Проявляется это на первой же сделке, требующей двух подписей.

<Hint type="tip">
В учебной сети `network.sh createChannel` объявляет опорные пиры сам — в выводе видны строки `Anchor peer set for org 'Org1MSP'`. В настоящей сети это отдельный шаг.
</Hint>

## Как получаются блоки

В открытой сети блок появляется, когда кто-то выиграл соревнование. Здесь соревнования нет: блок собирает назначенная служба по трём простым правилам.

<Figure scheme="fn-batching" caption="Блок закрывается по первому сработавшему условию из трёх" />

В настройках это выглядит так:

```text
BatchTimeout: {"timeout":"2s"}
BatchSize: {"max_message_count":10, "preferred_max_bytes":524288, "absolute_max_bytes":103809024}
```

<SyntaxBreakdown parts={[
  { text: 'BatchTimeout: 2s', label: 'по времени', note: 'прошло две секунды с первой сделки в пачке — блок закрывается, даже если в нём одна запись' },
  { text: 'max_message_count: 10', label: 'по количеству', note: 'набралось десять сделок — блок закрывается, не дожидаясь таймаута' },
  { text: 'preferred_max_bytes: 512 КБ', label: 'по объёму', note: 'желательный потолок; одна сделка больше него сама по себе блок не разорвёт' },
  { text: 'absolute_max_bytes: 99 МБ', label: 'жёсткий потолок', note: 'больше этого блок быть не может ни при каких условиях' },
]} />

Отсюда два следствия, которые видно на практике сразу. Одиночная команда выполняется до двух секунд — это не тормоза, это таймаут пачки. А под нагрузкой задержка падает: блок закрывается по счётчику раньше таймаута.

## Почему нет откатов

Тип согласия между упорядочивателями записан там же:

```text
тип согласия: etcdraft
```

Это алгоритм с **выбранным лидером**: один упорядочиватель ведёт, остальные повторяют за ним и следят, жив ли он. Умер лидер — оставшиеся выбирают нового. Никаких параллельных цепочек при этом не возникает.

Отсюда главное практическое отличие от открытых сетей: **окончательность наступает сразу**. Сделка попала в блок — значит попала. Нет понятия «дождитесь двенадцати подтверждений», нет ситуации «более длинная ветка победила и ваша сделка исчезла». Вся логика ожидания, которую в открытых сетях пишут вокруг подтверждений, здесь не нужна.

<Hint type="important">
Ценой этому — доверие к составу упорядочивателей. Если все они принадлежат одной организации, она может перестать принимать чужие сделки. Поэтому в настоящей сети упорядочиватели держат разные организации, и это вопрос договора, а не алгоритма.
</Hint>

Проверить окончательность легко — высота цепочки растёт монотонно:

```bash
peer channel getinfo -c pgk
```

```text
Blockchain info: {"height":16,"currentBlockHash":"oBJv5Ze+nYyrtkzhdRYCJbsG2DhMkoxS3+5nG0r0mdI=","previousBlockHash":"+miykifz3th0/2OROHtXRRV998Z5oF1LeVLh8jDEjwo="}
```

## Типичные ошибки

**Ошибка 1. Имя в сертификате не совпало с адресом.**

```text
Error: failed to create deliver client for orderer: orderer client failed to connect to
localhost:7050: failed to create new connection: context deadline exceeded
```

Стучимся на `localhost`, а в сертификате упорядочивателя написано `orderer.example.com`. Лечится флагом `--ordererTLSHostnameOverride orderer.example.com` — он есть почти в каждой команде этой главы и выглядит как шум ровно до первого такого отказа.

**Ошибка 2. Забыли `--tls` и `--cafile`.**

Учебная сеть поднята с обязательным шифрованием. Без этих флагов соединение не установится вообще, а сообщение будет про таймаут — то есть совершенно не про причину.

**Ошибка 3. Попытка прочитать `.pb` глазами.**

Блок настроек — двоичный protobuf. `cat` покажет мусор. Нужен `configtxlator proto_decode`.

**Ошибка 4. Правка политики на нижнем уровне вместо верхнего.**

Хотели «пусть подтверждать может одна организация», полезли в `Org1MSP` и поменяли там. Не сработает: «сколько организаций» задаётся на уровне канала (`MAJORITY` → `ANY`), а внутри организации написано только, чья подпись годится.
