## Зачем это нужно

Модуль сделан, всё работает, осталось сдать. И вот здесь теряются баллы, которые уже были заработаны.

Эксперт не смотрит на вашу папку. Он берёт то, что лежит **в репозитории**, разворачивает у себя и пробует запустить. Если проект не собирается — неважно, что у вас он собирался. Если в истории лежит сид-фраза — это снятые баллы за безопасность, даже если файл потом удалили.

Эта глава — про семь проверок, каждая на минуту, которые закрывают почти все потери такого рода. Всё ниже проделано вживую на учебном проекте: сначала с типичными ошибками, потом исправленном.

## «У меня работает» — не аргумент

<Figure scheme="sd-clean-clone" caption="У вас на диске и в чистом клоне — разные проекты" />

Соберём проект так, как его обычно собирает уставший человек за пять минут до конца времени:

```bash
git init
git add -A
git commit -m "первый коммит"
```

Смотрим, что реально попало:

```bash
git ls-files
```

```text
.env
node_modules/junk/a.js
package.json
src/index.ts
```

Четыре строки, и в них две беды сразу: в репозиторий уехал `.env` с сид-фразой и папка зависимостей. А `tsconfig.json`, `README.md` и файл блокировки версий — не уехали, потому что их просто нет.

<Hint type="important">
Команда `git ls-files` — самая недооценённая в этом списке. Она показывает ровно то, что увидит эксперт. Не `ls`, не «я вроде всё добавил», а именно она.
</Hint>

## Проверка первая: собрать из чистого клона

```bash
cd ..
git clone proekt proverka
cd proverka
ls -a
```

```text
. .. .git .gitignore package.json src
```

Ставим и собираем:

```bash
npm ci
npm run build
```

```text
Version 5.9.3
tsc: The TypeScript Compiler - Version 5.9.3

COMMON COMMANDS
```

Компилятор напечатал **справку**. Это не ошибка сборки — это `tsc`, запущенный без настроек: файла `tsconfig.json` в репозитории нет, компилировать нечего, и он показал, как им пользоваться.

## Проверка вторая: чего в репозитории быть не должно

```bash
printf 'node_modules/\ndist/\n.env\n' > .gitignore
git rm -r --cached node_modules .env
git add -A && git commit -m "убрал лишнее из репозитория"
git ls-files
```

```text
.gitignore
package.json
src/index.ts
```

<SyntaxBreakdown parts={[
  { text: '.gitignore', label: 'список игнорируемого', note: 'действует только на новые файлы: уже отслеживаемые он не выкинет' },
  { text: 'git rm -r --cached', label: 'убрать из индекса', note: 'ключевое слово --cached: файл остаётся на диске, но перестаёт отслеживаться' },
  { text: 'node_modules/', label: 'зависимости', note: 'сотни мегабайт, которые восстанавливаются одной командой — в репозитории им нечего делать' },
  { text: 'dist/', label: 'результат сборки', note: 'то же самое: собирается из исходников, хранить не нужно' },
]} />

<Hint type="important">
Добавить `.gitignore` **после** первого коммита недостаточно. Он не действует на файлы, которые уже отслеживаются, — их надо убирать руками через `git rm --cached`. Это ловушка, на которую попадаются почти все.
</Hint>

## Проверка третья: секрет остаётся в истории

Рабочая копия чистая. Проверим историю:

```bash
git show HEAD~1:.env
```

```text
SEED=olegs test seed for pgk champs course 2026
NODE_URL=http://127.0.0.1:6869
```

<Figure scheme="sd-secret-history" caption="Файл удалён, секрет достаётся одной командой" />

Сид-фраза на месте. Она в первом коммите, и там останется навсегда: история git неизменяема по устройству. Любой, у кого есть доступ к репозиторию — включая эксперта, — достанет её за одну команду.

Грепаем весь код и историю:

```bash
git grep -nEi "(api[_-]?key|secret|passw|seed *=)" -- .
```

```text
.env:1:SEED=olegs test seed for pgk champs course 2026
src/index.ts:1:const SEED = 'olegs test seed for pgk champs course 2026';
```

Второе попадание не менее важно: сид **вписан прямо в код**, и удаление `.env` его не трогает.

<Hint type="important">
Единственное настоящее лечение — **сменить ключ**. Переписывать историю можно, но ключ всё равно считается скомпрометированным: репозиторий мог быть склонирован, показан, попасть в резервную копию. На чемпионате это ещё и снятые баллы независимо от того, что вы сделали потом.
</Hint>

## Проверки с четвёртой по седьмую

<Figure scheme="sd-checklist" caption="Семь проверок, каждая на минуту" />

**Файл блокировки версий.** `package-lock.json` (или `yarn.lock`, `Gemfile.lock`, `poetry.lock`) должен быть в репозитории. Без него `npm ci` не работает вовсе, а `npm install` поставит новые версии — и проект, собиравшийся вчера, сегодня сломается.

**README с командами запуска.** Три команды подряд, которые можно скопировать:

```markdown
## Запуск

npm ci
npm run build
npm start
```

**Пример настроек.** Файл `.env.example` с перечнем переменных и **без значений**:

```text
SEED=
NODE_URL=http://127.0.0.1:6869
```

**Понятное падение без настроек.** Вот как выглядит плохо и хорошо:

```ts
const seed = process.env.SEED;
if (!seed) {
  throw new Error('Не задана переменная SEED — скопируйте .env.example в .env');
}
```

```text
Error: Не задана переменная SEED — скопируйте .env.example в .env
```

Вместо стека на сорок строк — одна строка, объясняющая, что делать.

```bash
git ls-files
```

```text
.env.example
.gitignore
README.md
package-lock.json
package.json
src/index.ts

```

Чистый клон:

```bash
git clone proekt proverka3 && cd proverka3

```

```text

код возврата: 0
```

Запуск без настроек:

```text
Error: Не задана переменная SEED — скопируйте .env.example в .env
```

Запуск с настройками:

```text
запуск с аккаунтом длиной 15
```

По дороге вылез ещё один реальный отказ: `error TS2580: Cannot find name 'process'. Do you need to install type definitions for node?` Типы Node не были записаны в зависимости. Заметить это можно было только на чистом клоне — на рабочей машине они лежали в папке зависимостей от соседнего проекта.
</Hint>

## Типичные ошибки

**Ошибка 1. Проверять на своей папке.**

Там лежит всё нужное, даже то, чего нет в репозитории. Проверка — только на чистом клоне.

**Ошибка 2. Считать `.gitignore` задним числом работающим.**

Не работает. Нужен `git rm --cached`.

**Ошибка 3. Коммитить `.env` «временно».**

Временного в истории git не бывает.

**Ошибка 4. README из одной строки «дипломный проект».**

README нужен эксперту, а не вам: три команды запуска и список переменных.

**Ошибка 5. Оставлять отладочный вывод с ключами.**

```js
console.log('сид:', seed);       // уедет в журнал, а журнал покажут
```

**Ошибка 6. Сдавать, не запустив.**

Последняя правка «на всякий случай» ломает сборку чаще, чем кажется. Между последним коммитом и поднятой рукой должен быть чистый клон.

## Что должен уметь после главы

- посмотреть, что реально лежит в репозитории, а не на диске;
- собрать проект из чистого клона и понять, чего не хватает;
- убрать лишнее из отслеживания и объяснить, почему `.gitignore` задним числом не работает;
- достать секрет из истории и объяснить, почему лечение — смена ключа;
- написать README и `.env.example`, которыми можно пользоваться;
- сделать так, чтобы программа без настроек падала понятно;
- пройти семь проверок за семь минут.
