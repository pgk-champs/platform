## Зачем это нужно

В критериях чемпионата по мобильной разработке есть отдельный список пунктов, и звучат они так:

```text
Создайте компоненты кнопок
Создайте инпут
Создайте компонент селект
Создайте компонент Поиск
Создайте компонент BottomSheet
Создайте компонент TabBar
Создайте компонент карточки
Создайте компонент «Хэдер»
Все компоненты библиотеки адаптивны
```

Девять оцениваемых пунктов, и каждый — про **свой** компонент, а не про использование готового из Material. Разница принципиальная: `Button` из Material вы вызываете, а `KitButtonPrimary` вы **проектируете** — решаете, какие у него параметры, какие состояния, что можно подменить снаружи.

Эта глава — про то, как устроен такой компонент, на примере кнопок. Дальше в блоке те же правила применяются к полям ввода, выбору, поиску и остальному списку.

<Hint type="important">
Весь Compose-код этой главы собран настоящим компилятором в библиотечном модуле Android: Kotlin 2.0.21, Compose BOM 2024.10.01, плагин сборки 8.7.3, compileSdk 34. Сообщения об ошибках ниже — его подлинный вывод, а не пересказ.
</Hint>

## Порядок параметров — это документация

<Figure scheme="kb-api-shape" caption="Обязательные, потом modifier, потом состояния, слоты последними" />

Порядок параметров в Compose — жёсткое соглашение, и следовать ему стоит не из вежливости: по нему чужой компонент читают, не открывая код.

```kotlin
@Composable
fun KitButtonPrimary(
    text: String,
    onClick: () -> Unit,
    modifier: Modifier = Modifier,
    enabled: Boolean = true,
    loading: Boolean = false,
    leading: (@Composable () -> Unit)? = null,
) {
    Button(
        onClick = onClick,
        modifier = modifier,
        enabled = enabled && !loading,
    ) {
        KitButtonContent(text = text, loading = loading, leading = leading)
    }
}
```

<SyntaxBreakdown parts={[
  { text: 'text: String, onClick: () -> Unit', label: 'обязательные — первыми', note: 'без умолчаний: кнопка без текста и без действия бессмысленна, и компилятор об этом напомнит' },
  { text: 'modifier: Modifier = Modifier', label: 'первый необязательный', note: 'соглашение всего Compose; вызывающий всегда знает, где искать место для отступов и размеров' },
  { text: 'enabled: Boolean = true', label: 'состояние с умолчанием', note: 'разумное значение по умолчанию: кнопка обычно доступна' },
  { text: 'enabled = enabled && !loading', label: 'состояния не независимы', note: 'во время загрузки кнопка недоступна — иначе пользователь нажмёт второй раз' },
  { text: 'leading: (@Composable () -> Unit)? = null', label: 'слот — последним', note: 'необязательный кусок разметки; ставят в конец, чтобы вызов мог закончиться лямбдой' },
]} />

<Hint type="tip">
`modifier: Modifier = Modifier` выглядит как тавтология, но это не она: слева — имя параметра, справа — объект-пустышка `Modifier`, к которому вызывающий добавляет что хочет. Компонент обязан его принять и повесить на свой **корневой** элемент — иначе снаружи невозможно ни задать отступ, ни растянуть кнопку по ширине.
</Hint>

## Три варианта, а не три цвета

<Figure scheme="kb-three-variants" caption="Вариант выбирают по важности действия, а не по красоте" />

На макете обычно три кнопки, и отличаются они не оттенком, а **весом действия**:

```kotlin
@Composable
fun KitButtonSecondary(
    text: String,
    onClick: () -> Unit,
    modifier: Modifier = Modifier,
    enabled: Boolean = true,
    loading: Boolean = false,
    leading: (@Composable () -> Unit)? = null,
) {
    OutlinedButton(
        onClick = onClick,
        modifier = modifier,
        enabled = enabled && !loading,
    ) {
        KitButtonContent(text = text, loading = loading, leading = leading)
    }
}

@Composable
fun KitButtonGhost(
    text: String,
    onClick: () -> Unit,
    modifier: Modifier = Modifier,
    enabled: Boolean = true,
) {
    TextButton(onClick = onClick, modifier = modifier, enabled = enabled) {
        Text(text = text, style = MaterialTheme.typography.labelLarge)
    }
}
```

Обратите внимание: у призрачной кнопки **нет** `loading` и `leading`. Это не забывчивость — так проектируют. Третьестепенное действие («Отмена», «Пропустить») не бывает долгим и не носит иконку; лишние параметры только создали бы впечатление, что ими можно пользоваться.

<Hint type="important">
Три варианта — три отдельные публичные функции, а не одна с параметром `variant: ButtonVariant`. Так вызов читается без заглядывания в перечисление (`KitButtonGhost("Отмена")` понятно сразу), а каждый вариант может иметь свой набор параметров. Параметр-перечисление берут, когда вариантов много и они правда одинаковы по возможностям.
</Hint>

## Слот вместо флагов

<Figure scheme="kb-slot-vs-flag" caption="Флаги растут с каждым пожеланием, слот не растёт вовсе" />

Дизайнер просит иконку слева от текста. Первое решение, которое приходит в голову:

```kotlin
showIcon: Boolean = false,
iconRes: Int? = null,
iconTint: Color? = null,
```

Через неделю просят бейдж с количеством — ещё три параметра. Потом индикатор загрузки вместо иконки — ещё два. Компонент превращается в свалку настроек, из которых в каждом конкретном вызове используются две.

Слот решает это целиком:

```kotlin
leading: (@Composable () -> Unit)? = null,
```

Вызывающий кладёт туда что угодно: иконку, бейдж, картинку, вообще всё, что рисуется. Компонент про это ничего не знает — он просто ставит содержимое слева и отступ после него.

```kotlin
@Composable
private fun KitButtonContent(
    text: String,
    loading: Boolean,
    leading: (@Composable () -> Unit)?,
) {
    Row(verticalAlignment = Alignment.CenterVertically) {
        if (loading) {
            CircularProgressIndicator(
                modifier = Modifier.size(16.dp),
                strokeWidth = 2.dp,
            )
            Spacer(modifier = Modifier.width(8.dp))
        } else if (leading != null) {
            leading()
            Spacer(modifier = Modifier.width(8.dp))
        }
        Text(text = text, style = MaterialTheme.typography.labelLarge)
    }
}
```

  { text: '(@Composable () -> Unit)?', label: 'тип слота', note: 'функция без аргументов, которая рисует; знак вопроса делает слот необязательным' },

  { text: 'leading()', label: 'вызов слота', note: 'компонент вызывает переданную разметку в том месте, где она должна оказаться' },

]} />

## Три ошибки, которые ловит компилятор

**Ошибка 1. Забыли `@Composable` у функции.**

```kotlin
fun Screen() { Text("привет") }
```

```text
e: Probe.kt:3:5 Functions which invoke @Composable functions must be marked with the @Composable annotation
e: Probe.kt:3:16 @Composable invocations can only happen from the context of a @Composable function
```

Две строки на одну ошибку: первая говорит, что делать, вторая — где именно сломалось.

**Ошибка 2. Слот объявлен без `@Composable` в типе.**

```kotlin
@Composable fun Card(slot: () -> Unit) { slot() }
@Composable fun Use() { Card(slot = { Text("внутри") }) }
```

```text
e: Probe.kt:5:39 @Composable invocations can only happen from the context of a @Composable function
```

Смотрите на позицию: `5:39` — это **место вызова**, внутри лямбды с `Text`. Сам `Card` скомпилировался нормально: обычная функция без аргументов — законный тип. Сломалось там, где в неё попытались положить разметку. Отсюда правило: аннотацию пишут внутри скобок типа — `(@Composable () -> Unit)`.

**Ошибка 3. Разметка в обработчике нажатия.**

```kotlin
@Composable fun P() { Button(onClick = { Text("нельзя") }) { Text("ок") } }
```

```text
e: Probe.kt:5:42 @Composable invocations can only happen from the context of a @Composable function
```

`onClick` — обычная функция, она выполняется по нажатию, а не во время отрисовки. Рисовать из неё нечего и некуда. Если по нажатию должно что-то появиться — меняют состояние, а разметка реагирует на изменение сама.

<Hint type="fact">
Все три ошибки дают одно и то же сообщение `@Composable invocations can only happen from the context of a @Composable function`. Разными у них будут только строка и столбец. Поэтому первое, что делают с этой ошибкой, — смотрят не на текст, а на позицию.
</Hint>

## А эту компилятор не ловит

```kotlin
@Composable
fun P() {
    val s = mutableStateOf(0)
    Text(s.value.toString())
}
```

```text
(сборка проходит, ошибок нет)
```

Состояние без `remember` создаётся заново при каждой перерисовке, и значение всегда сбрасывается. Компилятор молчит — это законный код, просто бесполезный. Предупреждение выдаст только проверка стиля в среде разработки, и то если она включена.

<Hint type="important">
Это разделение стоит запомнить на весь блок: компилятор проверяет **типы и контекст**, а не смысл. Всё, что связано с жизненным циклом состояния и с тем, перерисуется ли компонент, ловится только чтением кода и запуском.
</Hint>

## Типичные ошибки проектирования

**Ошибка 1. Компонент не принимает `modifier`.**

Снаружи такому компоненту ни отступ не задать, ни ширину. Лечится добавлением параметра и передачей его на корневой элемент — но обычно к этому моменту компонент уже вызван в двадцати местах с обёрткой `Box` вокруг.

**Ошибка 2. `modifier` повешен не на корень.**

```kotlin
Button(onClick = onClick) {
    Row(modifier = modifier) { … }   // отступ окажется ВНУТРИ кнопки
}
```

Снаружи задали `padding(16.dp)`, ожидая отступ вокруг кнопки, а получили увеличенную кнопку.

**Ошибка 3. Состояния не согласованы.**

`loading = true` при `enabled = true` — кнопка показывает индикатор и продолжает нажиматься. Пользователь оформит заказ дважды.

**Ошибка 4. Цвета и размеры вписаны числами внутри компонента.**

Библиотека на то и библиотека, что берёт значения из темы: `MaterialTheme.typography.labelLarge`, а не `fontSize = 14.sp`. Иначе смена темы не дойдёт до компонента.

**Ошибка 5. Слот сделан обязательным.**

`leading: @Composable () -> Unit` без `?` и без умолчания заставляет каждый вызов писать пустую лямбду. Необязательное делают необязательным.
