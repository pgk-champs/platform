## «Я же проверил руками» — почему этого не хватает

Модуль Е в конкурсном задании сформулирован в двух предложениях:

> Создайте тесты состояний в библиотеке UIKit к следующим компонентам: Поле для ввода, Селект, Кнопки, BottomTabBar, Карточка. Создайте тесты на библиотеку сетевого слоя **на каждый из запросов**, по тест-кейсам.

Весит он 4,7 балла — немного. Но большинство участников теряют на нём не баллы, а **время**: тесты пишут в последний час, впопыхах, и половина из них не компилируется. А ещё это единственный модуль, где эксперт видит не «работает ли», а «понимает ли участник, что именно должно работать».

Главный аргумент против тестов звучит одинаково у всех: «я запустил, нажал, увидел — работает». Ниже — почему этого недостаточно, на живом примере с валидацией email из этого же задания.

## Не один пример, а набор кейсов

Требование к email из задания: «name@domenname.ru», только строчные латинские буквы и цифры. Три реализации, которые пишут участники — от наивной до правильной. Проверим их так, как проверяют руками: три адреса. А потом — так, как проверяет тест: четырнадцать.

<KotlinPlay code={`// Три реализации одной и той же проверки email из КЗ: «name@domenname.ru»,
// только строчные латинские буквы и цифры.

fun naive(email: String) = email.contains("@") && email.contains(".")

val pattern = Regex("[a-z0-9]+@[a-z0-9]+\\\\.ru")

fun search(email: String) = pattern.containsMatchIn(email)  // ищет вхождение
fun strict(email: String) = pattern.matches(email)          // требует совпадения целиком

// Набор тест-кейсов: строка → каким должен быть ответ.
val eyeball = listOf(

    "ivan@mail" to false,
    "ivanmail.ru" to false

val full = eyeball + listOf(

    for ((input, expected) in cases) if (f(input) != expected) fails += input
    val mark = if (fails.isEmpty()) "ЗЕЛЁНЫЙ" else "КРАСНЫЙ"

<Figure scheme="tm-coverage" caption="На трёх кейсах все три реализации зелёные и неразличимы; разницу показал только набор из четырнадцати" />

Наивная проверка через `contains("@")` — ошибка, которую все ждут. Неожиданное здесь другое: **почти правильный** регекс с `containsMatchIn` пропускает четыре адреса. Он ищет *вхождение* образца в строку, а не совпадение целиком — поэтому `«Иван <ivan@mail.ru> и ещё текст»` для него валидный email. Это та же ловушка, что `Pattern.matcher().find()` вместо `.matches()` в Java.

Глазом эту разницу не поймать: на трёх адресах, которые приходят в голову, обе реализации зелёные. Разницу видит только таблица «вход → ожидаемый выход» — и ценность её ровно в тех строках, которые руками никто не набирает: пробел по краям, заглавная буква, пустая строка, мусор вокруг правильного значения.

Тест — это и есть такая таблица, которая отрабатывает заново после каждой правки, а не один раз перед сдачей.

## Куда кладут тесты и как устроен один тест

В Android-проекте две папки для тестов, и это две разные вселенные:

| Папка | Что это | Как запускать | Скорость |
|---|---|---|---|
| `src/test/` | чистая JVM, без Android | `./gradlew test` | секунды |
| `src/androidTest/` | инструментальные, нужен эмулятор | `./gradlew connectedAndroidTest` | минуты |

Валидаторы, мапперы, `ViewModel`, сетевой слой через заглушку — всё это идёт в `src/test/`. В `src/androidTest/` остаётся только то, чему без эмулятора никак: тесты `Composable`.

Один тест внутри:

```kotlin
class EmailValidatorTest {

    @Test
    fun `заглавная буква не проходит`() {
        // Arrange — подготовка
        val input = "Ivan@mail.ru"

        // Act — действие
        val result = isValidEmail(input)

        // Assert — проверка
        assertEquals(false, result)
    }
}
```

## Два первых юнит-теста: валидатор из задания и маппер

Самые быстрые баллы — тесты на то, что уже сформулировано в задании. Email по паттерну и пароль не короче восьми символов — это готовые тест-кейсы, их пишут первыми:

```kotlin
class ValidatorsTest {

    @Test
    fun `корректный email проходит`() = assertTrue(isValidEmail("ivan2024@shop.ru"))

    @Test
    fun `заглавная буква не проходит`() = assertFalse(isValidEmail("Ivan@mail.ru"))

    @Test
    fun `пробел по краям не проходит`() = assertFalse(isValidEmail(" ivan@mail.ru"))

    @Test
    fun `домен не ru не проходит`() = assertFalse(isValidEmail("ivan@mail.com"))

    @Test
    fun `пароль из 7 символов не проходит`() = assertFalse(isValidPassword("1234567"))

    @Test
    fun `пароль из 8 символов проходит`() = assertTrue(isValidPassword("12345678"))
}
```

Второй кандидат — маппер `ProductDto → Product` из главы про слои. Он тоже чистая функция без Android внутри:

```kotlin
@Test
fun `цена из копеек превращается в рубли`() {
    val dto = ProductDto(id = 1, title = "Кофе", priceKopecks = 25000)

    val product = dto.toDomain()

    assertEquals(250.0, product.price, 0.001)
}
```

Оба класса — образец для всех остальных: функция принимает данные, возвращает результат, тест сравнивает результат с ожиданием. Ничего не мокается, ничего не поднимается.

<Hint type="tip">
`assertEquals` для `Double` принимает третий аргумент — допуск. Без него `0.1 + 0.2` не равно `0.3`, и тест упадёт на арифметике с плавающей точкой, а не на вашей логике.
</Hint>

## Что мешает тесту: сеть, время, база — и чем их заменяют

Валидатор тестируется напрямую. А `Repository`, который ходит в сеть? Если тест по-настоящему сходит на сервер, он будет медленным, будет падать при отсутствии интернета и не сможет проверить ветку «сервер вернул 500», потому что сервер её просто не вернёт по заказу.

Зависимость заменяют **тестовым дублем**. Их четыре вида, и на практике в этой главе нужен один:

- **Фейк** — упрощённая рабочая реализация. Вместо сети — список в памяти. Обычный Kotlin-класс, никаких библиотек.
- **Стаб** — отдаёт заготовленные ответы, логики нет.
- **Мок** — записывает вызовы, чтобы потом проверить: «метод вызван один раз с такими аргументами». Обычно через библиотеку.
- **Шпион** — настоящий объект, обёрнутый записью вызовов.

Google в документации по тестовым дублям прямо пишет: фейки предпочтительнее — не требуют библиотеки моков и остаются обычными классами. Для чемпионата это ещё и практический довод: библиотеку моков нужно помнить наизусть, а фейк — это `class` с `override`.

## Фейк вместо мока: подмена дефолтным параметром

Один и тот же тест репозитория — против «настоящей» сети (задержка 300 мс и 15 % случайных отказов) и против фейка. Двадцать прогонов:

<KotlinPlay code={`import kotlinx.coroutines.*
import kotlin.random.Random

// Зависимость описана интерфейсом — этого достаточно, чтобы её подменить.
interface ProductApi {
    suspend fun load(): List<String>
}

// «Настоящая» реализация: ходит по сети. Медленно и иногда падает.
class RealProductApi(private val rnd: Random) : ProductApi {
    override suspend fun load(): List<String> {
        delay(300)                                   // сеть отвечает не мгновенно
        if (rnd.nextInt(100) < 15) throw RuntimeException("timeout")
        return listOf("Кофе", "Чай", "Какао")
    }
}

// Фейк: та же роль, поведение задано вручную. Ещё и считает обращения.
class FakeProductApi(
    private val answer: List<String> = listOf("Кофе", "Чай", "Какао"),
    private val fail: Boolean = false
) : ProductApi {
    var calls = 0
        private set

    override suspend fun load(): List<String> {
        calls++
        if (fail) throw RuntimeException("нет соединения")
        return answer
    }
}

// Граф собирается дефолтными параметрами конструктора.
// В приложении пишут ProductRepository() — подставится настоящая реализация.
// В тесте передают фейк, и больше ничего менять не надо.
class ProductRepository(private val api: ProductApi = RealProductApi(Random)) {
    private var cache: List<String>? = null

    suspend fun products(): List<String> {
        cache?.let { return it }
        return api.load().also { cache = it }
    }
}

fun measure(times: Int, block: suspend () -> Unit): Pair<Long, Int> {
    var failed = 0
    val start = System.nanoTime()
    runBlocking {
        repeat(times) {
            try { block() } catch (e: Exception) { failed++ }
        }
    }
    return (System.nanoTime() - start) / 1_000 to failed   // микросекунды
}

fun main() {
    val runs = 20

    println("── один и тот же тест против настоящей реализации ($runs прогонов) ──")
    val seeded = Random(2026)
    val (usReal, failReal) = measure(runs) {
        val list = ProductRepository(RealProductApi(seeded)).products()
        check(list.size == 3)
    }
    println("  время:  \${usReal / 1000} мс")
    println("  упало:  $failReal из $runs   ← код не менялся, «моргнула» сеть")

    println()
    println("── тот же тест против фейка ($runs прогонов) ──")
    val fake = FakeProductApi()
    val (usFake, failFake) = measure(runs) {
        val list = ProductRepository(fake).products()
        check(list.size == 3)
    }
    println("  время:  $usFake мкс  (\${usFake / 1000} мс)")
    println("  упало:  $failFake из $runs")
    println("  разница по времени: в \${usReal / maxOf(usFake, 1)} раз")

    println()
    println("── что фейк умеет, а настоящая реализация нет ──")
    runBlocking {
        val counting = FakeProductApi()
        val repo = ProductRepository(counting)
        repeat(5) { repo.products() }
        println("  5 обращений к репозиторию → вызовов api: \${counting.calls}  (работает кэш)")

        val broken = ProductRepository(FakeProductApi(fail = true))
        val text = try { broken.products().toString() } catch (e: Exception) { "ошибка: \${e.message}" }
        println("  сценарий «нет сети» воспроизведён на заказ → $text")
    }
}`} />

<Figure scheme="tm-fake-vs-real" caption="Одна зависимость, две реализации: настоящая — шесть секунд и два случайных падения, фейк — микросекунды и ноль" />

Три числа. **Шесть секунд против 183 микросекунд** — в тридцать три тысячи раз. **Два падения из двадцати** на коде, который не менялся — вот откуда берутся «мигающие» тесты, которым перестают верить и которые потом отключают. И **счётчик вызовов**: фейк знает, сколько раз его дёрнули, и тест проверяет, что кэш работает — пять обращений к репозиторию, один поход в «сеть».

Как фейк попадает внутрь без DI-фреймворка — дефолтным параметром конструктора:

```kotlin
class ProductRepository(private val api: ProductApi = RealProductApi())
```

В приложении пишут `ProductRepository()` — подставится настоящая реализация. В тесте — `ProductRepository(FakeProductApi())`. Ничего больше менять не нужно. Это работает, потому что зависимость объявлена **интерфейсом**, а не конкретным классом: и настоящая реализация, и фейк — просто два `ProductApi`.

## Тест ViewModel: runTest и главный диспетчер

`ViewModel` тестируется так же — с фейком репозитория. Но у неё две особенности, из-за которых первый тест почти всегда падает.

Первая: код в ней асинхронный. Тест оборачивают в `runTest` — он перематывает `delay` мгновенно и ждёт завершения корутин:

```kotlin
@Test
fun `после загрузки в состоянии список товаров`() = runTest {
    val vm = ProductsViewModel(ProductRepository(FakeProductApi()))

    vm.load()
    advanceUntilIdle()

    assertEquals(listOf("Кофе", "Чай", "Какао"), vm.state.value.products)
}
```

Вторая: `viewModelScope` живёт на `Dispatchers.Main`, а в JVM-тесте главного потока нет. Падение выглядит так:

```text
IllegalStateException: Module with the Main dispatcher is missing.
Add dependency providing the Main dispatcher, e.g. 'kotlinx-coroutines-android'
```

Совет в сообщении — ложный след. Зависимость добавлять не нужно; нужно подменить главный диспетчер тестовым:

```kotlin
class MainDispatcherRule : TestWatcher() {
    private val dispatcher = StandardTestDispatcher()
    override fun starting(description: Description) = Dispatchers.setMain(dispatcher)
    override fun finished(description: Description) = Dispatchers.resetMain()
}

class ProductsViewModelTest {
    @get:Rule
    val mainRule = MainDispatcherRule()
    // ...
}
```

Правило пишется один раз и подключается в каждый тестовый класс `ViewModel`. Его набирают по памяти — на чемпионате интернета десять минут.

<Hint type="important">
`runBlockingTest`, `TestCoroutineDispatcher` и `TestCoroutineScope` устарели. В руководствах 2021–2023 годов они везде — не копируйте. Актуально: `runTest` с `StandardTestDispatcher`. У `runTest` таймаут 60 секунд по умолчанию: если тест «висит минуту и падает», скорее всего кто-то ждёт ответа, который не был поставлен в очередь.
</Hint>

## MockWebServer: настоящий HTTP, ненастоящий сервер

Фейк проверяет репозиторий. Но сам сетевой слой — `Retrofit`, конвертер JSON, интерсептор с токеном — фейком не проверишь: фейк его обходит. Для этого есть `MockWebServer` из OkHttp: локальный HTTP-сервер, который отвечает тем, что вы положили в очередь.

```kotlin
class ProductApiTest {
    private val server = MockWebServer()
    private lateinit var api: ProductApi

    @Before
    fun setUp() {
        server.start()
        api = Retrofit.Builder()
            .baseUrl(server.url("/"))
            .addConverterFactory(GsonConverterFactory.create())
            .build()
            .create(ProductApi::class.java)
    }

    @After
    fun tearDown() = server.shutdown()

    @Test
    fun `успешный ответ разбирается в список`() = runTest {
        server.enqueue(MockResponse().setResponseCode(200).setBody("""[{"id":1,"title":"Кофе"}]"""))

        val products = api.getProducts()

        assertEquals(1, products.size)
        assertEquals("Кофе", products[0].title)
    }
}
```

Запрос идёт по **настоящему HTTP** на `localhost` — значит, проверяется весь слой целиком: как `Retrofit` построил URL, как конвертер разобрал JSON, что интерсептор добавил заголовок.

<Hint type="fact">
`MockWebServer` живёт в двух артефактах: старый `com.squareup.okhttp3:mockwebserver` (пакет `okhttp3.mockwebserver`, `MockResponse().setResponseCode(200).setBody(...)`) и новый `mockwebserver3` (неизменяемый `MockResponse(body = ...)`, тело запроса — `ByteString?`). API у них разное, и копипаста из руководства 2023 года под новый артефакт не соберётся. В главе — старый, он проще и по-прежнему выпускается.
</Hint>

## Проверять не только ответ, но и тело запроса

Заглушка отвечает заготовкой на **что угодно**. Отсюда ловушка, из-за которой на чемпионате теряют баллы молча:

<KotlinPlay code={`// Модель MockWebServer: заготовленные ответы в очереди и журнал принятых запросов.

class MockServer {
    private val answers = ArrayDeque<String>()
    private val received = ArrayDeque<Recorded>()

    fun enqueue(json: String) { answers.addLast(json) }

    fun handle(method: String, path: String, body: String): String {
        received.addLast(Recorded(method, path, body))
        return answers.removeFirstOrNull() ?: error("очередь ответов пуста")
    }

    fun takeRequest(): Recorded =
        received.removeFirstOrNull() ?: error("запросов не было")
}

## Тест-кейсы на каждый запрос

Формулировка задания — «на каждый из запросов, по тест-кейсам». Это буквально: пять методов в интерфейсе `ApiService` — минимум пять тестовых методов. Эксперт считает соответствие.

А «по тест-кейсам» означает, что у одного запроса не одна ветка. Минимальный набор на каждый:

| Тест-кейс | Что кладём в очередь | Что проверяем |
|---|---|---|
| Успех | `200` + корректный JSON | разобранная модель, тело запроса |
| Не авторизован | `401` | клиент бросает ожидаемое исключение или возвращает ошибку |
| Сервер упал | `500` | то же — приложение не падает |
| Битый JSON | `200` + `{"id":` | ошибка разбора обработана, не `crash` |

```kotlin
@Test
fun `401 превращается в ошибку авторизации`() = runTest {
    server.enqueue(MockResponse().setResponseCode(401))

    val result = repository.loadProducts()

    assertTrue(result is Result.Error)
    assertEquals(AppError.Unauthorized, (result as Result.Error).error)
}
```

Это тот же перевод кодов в понятные ошибки из главы про сетевые ошибки — только теперь каждая ветка закреплена тестом, и при рефакторинге сетевого слоя её невозможно сломать незаметно.

## Тесты Composable: семантическое дерево

Тесты интерфейса живут в `src/androidTest/` и работают через `createComposeRule()`. Тест видит не пиксели, а **дерево семантики** — то же, что читает экранный диктор:

```kotlin
class PrimaryButtonTest {
    @get:Rule
    val composeRule = createComposeRule()

    @Test
    fun `отключённая кнопка не реагирует на нажатие`() {
        var clicks = 0
        composeRule.setContent {
            PrimaryButton(text = "Войти", enabled = false, onClick = { clicks++ })
        }

        composeRule.onNodeWithText("Войти").assertIsNotEnabled()
        composeRule.onNodeWithText("Войти").performClick()

        assertEquals(0, clicks)
    }
}
```

Инструменты, которые нужны на практике:

- **Найти узел** — `onNodeWithText`, `onNodeWithTag`, `onNodeWithContentDescription`. Тег ставится модификатором `Modifier.testTag("email_field")` и нужен там, где текст меняется.
- **Проверить** — `assertIsDisplayed`, `assertIsEnabled` / `assertIsNotEnabled`, `assertTextEquals`, `assertIsSelected`.
- **Действовать** — `performClick`, `performTextInput`, `performScrollTo`. Каждое действие — отдельный вызов, объединять нельзя.
- **Отладить** — `onRoot().printToLog("TAG")` печатает всё дерево в Logcat.

<Hint type="important">
`onNodeWithTag` не находит узел, хотя `testTag` стоит: `Expected exactly '1' node but could not find any`. Причина — родитель (`Row` с `clickable`, `Button`, `ListItem`) слил семантику детей, и поиск идёт по слитому дереву. Лечится параметром `useUnmergedTree = true`; найти виновника помогает `printToLog`.
</Hint>

## Тесты состояний UI Kit по формулировке задания

«Тесты состояний» — не «компонент отрисовался». Проверяется каждое состояние из главы про UI Kit:

| Компонент | Состояния, на которые нужен тест |
|---|---|
| Поле для ввода | пустое, заполненное, с ошибкой, отключённое |
| Селект | закрытый, раскрытый, с выбранным значением |
| Кнопка | обычная, нажатие вызывает `onClick`, отключённая не вызывает |
| BottomTabBar | выбранная вкладка подсвечена, нажатие переключает |
| Карточка | с картинкой и без, нажатие вызывает обработчик |

Один компонент — один тестовый класс, одно состояние — один метод. Для поля ввода:

```kotlin
@Test
fun `ошибка показывается под полем`() {
    composeRule.setContent {
        AppTextField(value = "ivan@mail", onValueChange = {}, error = "Неверный формат")
    }

    composeRule.onNodeWithText("Неверный формат").assertIsDisplayed()
}

@Test
fun `без ошибки подписи нет`() {
    composeRule.setContent {
        AppTextField(value = "ivan@mail.ru", onValueChange = {}, error = null)
    }

    composeRule.onNodeWithText("Неверный формат").assertDoesNotExist()
}
```

Пять компонентов по три–четыре состояния — пятнадцать-двадцать коротких тестов. Каждый — пять строк. Это час работы, если UI Kit собран как отдельный модуль с чистыми параметрами; и нерешаемая задача, если компоненты тянут `ViewModel` внутрь.

## TDD: три коммита RED / GREEN / REFACTOR

В части заданий есть отдельное требование — разработка через тестирование с тремя коммитами:

1. **RED** — тест написан, код ещё нет; тест падает. Коммит.
2. **GREEN** — минимальный код, чтобы тест позеленел. Коммит.
3. **REFACTOR** — уборка без единой правки теста. Коммит.

И ограничение, написанное в задании прямо: «в случае изменения теста на данном этапе тест не будет учитываться в оценке». Тест из коммита RED обязан **дословно** совпадать с тестом в GREEN и REFACTOR. Переписали ассерт под получившийся код — тест обнулён. Ошибки нет, сборка зелёная, оценка ноль.

Если тест из RED оказался неверным — честнее оставить его красным и написать рядом новый, чем править.

```text
git log --oneline
a1b2c3d  REFACTOR: вынести регекс email в константу
d4e5f6a  GREEN: isValidEmail по паттерну задания
b7c8d9e  RED: тесты валидатора email
```

Практический смысл TDD для четырёхчасового модуля — не философия, а порядок: тест на валидатор пишется за две минуты, и он сразу фиксирует, что именно требуется. Код, написанный под готовый тест, редко приходится переделывать.

## Типичные ошибки

**Проверен только ответ, `takeRequest()` не вызван.** Тест зелёный на неправильном запросе. На живом API — `400`, после сдачи.

**Тест поправлен после RED.** По правилам задания не учитывается. Сборка зелёная, оценка ноль.

**Тесты в `src/androidTest/`, гоняют `./gradlew test`.** `BUILD SUCCESSFUL`, тесты ни разу не запускались.

**`assertEquals(получили, ожидали)`.** Работает, но сообщение об ошибке врёт наоборот — отладка идёт не туда.

**`ViewModel` без `MainDispatcherRule`.** `Module with the Main dispatcher is missing` — и ложный совет в тексте ошибки.

**`onNodeWithTag` не находит узел.** Родитель слил семантику; нужен `useUnmergedTree = true`.

**Один фейк на весь класс.** Счётчик или кэш дожил из предыдущего теста; падает то один тест, то другой. Фейк создаётся в `@Before`.

**Тестовый класс с опечаткой.** Не компилируется один — не компилируется весь `sourceSet`, модуль обнуляется целиком. Перед сдачей — `./gradlew test`, не только сборка приложения.

## На чемпионате

Как эксперт проверяет модуль Е:

- **Считает.** Пять методов в `ApiService` — ищет пять тестовых методов. Пять компонентов UI Kit — пять тестовых классов. Несоответствие видно за минуту.
- **Запускает.** `./gradlew test` — если один класс не компилируется, весь модуль обнуляется. Проверьте это сами перед сдачей.
- **Смотрит на тест-кейсы.** Один тест «успех» на запрос — минимум. Ветки `401` и `500` показывают, что участник понимает, зачем тесты.
- **Сверяет коммиты TDD**, где они требуются: тест в RED и в GREEN — один и тот же файл, `git diff` между коммитами по тестовому классу пустой.
- **Читает шапку класса** — комментарий с датой и номером участника, как в боевом коде.

Порядок работы на четыре часа: валидаторы и мапперы (десять минут, готовые тест-кейсы из задания) → `MockWebServer` на каждый запрос (успех, `401`, `500`) → состояния UI Kit. Тесты `ViewModel` — если осталось время.

Интернета десять минут на человека за сессию. Скелет теста, `MainDispatcherRule`, обвязка `MockWebServer` с `@Before`/`@After` — набираются по памяти. Тренажёр выше — ровно для этого.

## Углубиться

- **Robolectric** — тесты `Composable` на чистой JVM без эмулятора: `@RunWith(RobolectricTestRunner::class)` и `isIncludeAndroidResources = true`. Заметная экономия времени, но как приём, а не основной путь.
- **Turbine** — библиотека для тестов `Flow`: `flow.test { assertEquals(x, awaitItem()) }` вместо ручного сбора.
- **Параметризованные тесты** — одна функция, таблица входов: тот же принцип, что в модели с четырнадцатью адресами, но средствами JUnit.
- **MockK** — когда фейка не хватает и нужно проверить, что метод вызван с конкретными аргументами.
- **Скриншот-тесты** — сравнение отрисовки с эталонной картинкой; ловят то, что семантическое дерево не видит.
